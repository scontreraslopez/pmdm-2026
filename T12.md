# T12 · Integración con Firebase y empaquetado para Play Store

## Introducción a Firebase Authentication

Una de las funcionalidades más ubicuas en las aplicaciones móviles es la autenticación de usuarios. Firebase Authentication es una solución robusta y fácil de implementar que permite a los desarrolladores integrar múltiples métodos de autenticación en sus aplicaciones, como correo electrónico, Google, Facebook, entre otros.

Empecemos por hablar de Firebase. **Firebase** es una plataforma de desarrollo de aplicaciones móviles y web que ofrece una variedad de servicios, incluyendo autenticación, base de datos en tiempo real, almacenamiento en la nube y análisis. Firebase Authentication es uno de estos servicios y facilita la implementación de sistemas de autenticación seguros y escalables. Es lo que se conoce como **Backend as a Service (BaaS)**, ya que proporciona una infraestructura backend lista para usar, permitiendo a los desarrolladores centrarse en la creación de la experiencia del usuario sin preocuparse por la gestión del servidor. Otro popular **BaaS** es **Supabase**, que también ofrece servicios similares a Firebase, pero con un enfoque en bases de datos SQL (postgrest) y código abierto. Para entrar a la consola de Firebase, se puede acceder a través de [Firebase Console](https://console.firebase.google.com/).

El tema de la autenticación a través de Firebase lo podemos encontrar en [https://firebase.google.com/docs/auth?hl=es-419](https://firebase.google.com/docs/auth?hl=es-419). Nosotros nos decantaremos en la opción de **Quiero crear mi sistema de autenticación con Firebase**. Firebase cuenta para ello con **Firebase UI**, que es una biblioteca que proporciona una interfaz de usuario preconstruida para la autenticación, facilitando aún más la integración de múltiples métodos de inicio de sesión en las aplicaciones. Firebase UI soporta varios proveedores de autenticación, incluyendo correo electrónico y contraseña, Google, Facebook, Twitter, GitHub, y más. [https://firebase.google.com/docs/auth/android/firebaseui?hl=es-419](https://firebase.google.com/docs/auth/android/firebaseui?hl=es-419).

Lamentablemente, Firebase UI a fecha de hoy (Diciembre 2025) está todavía en beta para Jetpack Compose (`implementation("com.firebaseui:firebase-ui-auth:10.0.0-beta01")`), y la documentación oficial no está completa. Por lo que todavía tendremos que esperar un poco para tener una solución completamente integrada con Compose. Sin embargo, es posible integrar Firebase Authentication en aplicaciones Jetpack Compose utilizando las bibliotecas de Firebase y creando interfaces de usuario personalizadas.

### FASE 1: Preparación Técnica de la App

Antes de pensar en subir la app, debes asegurarte de que el código y los recursos estén listos para producción.

#### Configuración para el lanzamiento (Release)

El entorno de desarrollo es diferente al de producción. Debes realizar los siguientes ajustes en tu archivo `build.gradle` (o `build.gradle.kts`):

- **Desactivar la depuración (Debugging):** Es crucial por seguridad y rendimiento.
  - En el bloque `buildTypes > release`, asegúrate de configurar `debuggable false` (Groovy) o `isDebuggable = false` (Kotlin).
- **Desactivar el registro (Logging):** Elimina las llamadas a `Log` y cualquier archivo de prueba estático.
- **Identificador de la aplicación:** Asegúrate de que el `applicationId` sea el definitivo; no podrás cambiarlo una vez publicada la app.

#### Limpieza de recursos y código

- **Shrinking (Reducción):** Habilita la reducción (previamente ProGuard/R8) en tu build de release para eliminar código no usado y ofuscar clases.
- **Directorios:**
  - `src/`: Solo debe contener fuentes de tu app (Java/Kotlin).
  - `lib/`: Solo librerías de terceros necesarias. Elimina librerías de test.
  - `res/`: Elimina archivos *drawable*, *layout* o *values* antiguos que ya no se usen.
- **WebView:** Si usas WebViews, deshabilita la depuración de contenidos web con `WebView.setWebContentsDebuggingEnabled(false)`.

#### Revisión de Políticas (Play Policy Insights)

Android Studio incluye una herramienta para prevenir rechazos en la tienda.

- Ve a **Code > Inspect for Play Policy Insights**.
- Esto te mostrará advertencias sobre permisos o SDKs que podrían violar políticas de Google Play.

### FASE 2: Versionado y Compatibilidad

El versionado es vital para que los usuarios reciban actualizaciones y el sistema gestione la compatibilidad.

#### Configuración de Versiones

En tu archivo `build.gradle` a nivel de módulo, dentro de `defaultConfig`:

1. **`versionCode` (Entero positivo):** Es un número interno. **Debe aumentar** con cada actualización (ej. 1, 2, 3...). Google Play no permite subir un APK/AAB con un `versionCode` igual o inferior a uno ya existente.
2. **`versionName` (String):** Es lo que ve el usuario (ej. "1.0", "2.1-beta"). No tiene impacto técnico en la actualización.

#### Niveles de API (SDK)

Define en qué dispositivos funcionará tu app:

- **`minSdk`:** La versión mínima de Android requerida. Si el dispositivo tiene una versión inferior, no podrá instalar la app.
- **`targetSdk`:** La versión para la que diseñaste y probaste la app (generalmente la más reciente disponible).

### FASE 3: Firma de la Aplicación (Signing)

Android requiere que todas las apps estén firmadas digitalmente. Para Google Play, el estándar es **Play App Signing**.

#### Conceptos Clave

- **Upload Key (Clave de carga):** La generas tú y la guardas en tu PC. Se usa para firmar el AAB antes de subirlo a Google.
- **App Signing Key (Clave de firma de app):** Google gestiona esta clave. Google la usa para firmar los APKs que se distribuyen a los usuarios finales.

#### Cómo generar una clave de carga (Upload Key) en Android Studio

1. Ve a **Build > Generate Signed Bundle/APK**.
2. Selecciona **Android App Bundle** (Recomendado) o APK.
3. Haz clic en **Create new** bajo el campo "Key store path".
4. Rellena los datos:

- **Keystore path:** Dónde guardar el archivo `.jks`.
- **Password:** Contraseña fuerte para el almacén.
- **Alias:** Nombre para identificar tu clave.
- **Validity:** **Mínimo 25 años**. Google exige que la validez termine después del **22 de octubre de 2033**.

5. Finaliza el proceso para generar tu primera build firmada.

> **SEGURIDAD:** Nunca compartas tu clave privada ni las contraseñas del Keystore. Si pierdes la *Upload Key*, puedes pedir un reseteo en la Play Console, pero si pierdes la *App Signing Key* (en el caso de gestión manual antigua), no podrás actualizar la app nunca más.

---

### FASE 4: Construcción y Pruebas (Build & Test)

#### Generar el Artefacto

Usa la opción **Build > Generate Signed Bundle/APK** y selecciona la variante `release`.

- Esto generará un archivo `.aab` (App Bundle) optimizado y firmado.
- El App Bundle permite que Google Play genere APKs específicos para cada dispositivo (Dynamic Delivery), reduciendo el peso de descarga para el usuario.

#### Pruebas Finales

- **Dispositivos Reales:** Prueba en al menos un teléfono y una tablet.
- **Firebase Test Lab:** Útil para probar en múltiples configuraciones y versiones de Android en la nube.
- **Servidores Externos:** Si tu app usa backend, asegúrate de que las URLs apunten a los servidores de producción (no a los de desarrollo/test).

### FASE 5: Publicación en Google Play

Google Play es la plataforma principal para alcanzar una audiencia global.

#### Preparación de la Ficha

Antes de subir el binario, necesitas:

- **Icono de alta resolución.**
- **Capturas de pantalla (Screenshots):** Teléfono, tablet de 7", tablet de 10".
- **Texto promocional:** Título, descripción corta y descripción completa.
- **Gráfico de funciones:** Imagen promocional principal.

#### Subida a la Play Console

1. Crea una cuenta de desarrollador (si no la tienes).
2. Crea una nueva aplicación.
3. Configura **Play App Signing** (Google te guiará; generalmente usarás la clave que generaste en la Fase 3 como tu *Upload Key*).
4. Ve a la sección **Producción** o **Testing** (Alfa/Beta).
5. Sube tu archivo `.aab`.

#### Tipos de Lanzamiento (Tracks)

- **Pruebas Internas:** Rápido, para tu equipo. Puedes usar también *Firebase App Distribution*.
- **Pruebas Cerradas (Alfa):** Para un grupo pequeño de testers seleccionados.
- **Pruebas Abiertas (Beta):** Visible en la tienda para usuarios que quieran probar versiones tempranas.
- **Producción:** Lanzamiento general al público.

#### Revisión

Una vez que hagas clic en "Publicar", tu app pasará por una revisión de Google. Esto puede tardar desde unas horas hasta varios días.

---

### FASE 6: Alternativa - Publicación en Sitio Web

Si no quieres usar Google Play, puedes distribuir tu app directamente.

1. **Genera un APK firmado:** En lugar de un AAB, genera un APK desde Android Studio.
2. **Aloja el archivo:** Sube el APK a tu servidor web.
3. **Enlace de descarga:** Proporciona un link directo al usuario.

**Consideraciones para el usuario ("Orígenes desconocidos"):**

- **Android 8.0 (Oreo) y superior:** El usuario debe dar permiso explícito al navegador (ej. Chrome) para "Instalar aplicaciones desconocidas".
- **Android 7.1.1 y anterior:** El usuario debe activar la opción global "Orígenes desconocidos" en Seguridad.

**Desventajas de este método:**

- No tienes acceso a actualizaciones automáticas.
- No puedes usar Google Play Billing (compras in-app).
- Menor confianza del usuario debido a las advertencias de seguridad de Android.

### 🎯 Objetivo

Desarrollar la **lógica funcional y la implementación técnica** de la aplicación móvil cuya interfaz habéis diseñado en el módulo de *Desarrollo de Interfaces*. La aplicación debe ser funcional, robusta y conectar con servicios externos.

### 🧭 Contexto Técnico

La aplicación debe ser fiel al diseño visual aprobado (guía de estilo y wireframes de DIN) pero añadiendo la capa de inteligencia y datos.
La aplicación deberá gestionar:

- **Identidad:** Autenticación de usuarios en la nube.
- **Datos:** Persistencia y consulta de datos remotos (API REST).
- **Lógica de Negocio:** Gestión de reservas, validaciones y navegación.

### 📝 Consigna Técnica

#### 1. Arquitectura y Estructura

- El código debe estar estructurado, documentado y ser mantenible.
- Se valorará el uso de patrones de diseño vistos en clase (MVVM, Clean Architecture, o separación por paquetes lógicos).
- **Coherencia Visual:** Debes implementar los layouts (Jetpack Compose) respetando la paleta de colores y tipografía definidas en tu guía de estilo de DIN.

#### 2. Funcionalidad Backend (API REST)

- La app debe consumir información de vuestro backend mediante **Retrofit**.
- Debe manejar correctamente los estados de carga (loading) y posibles errores de conexión (feedback al usuario).

#### 3. Autenticación (Firebase)

- Implementar login y registro funcional utilizando **Firebase Authentication**.
- Gestión de sesión (mantener la sesión iniciada o cerrar sesión).

#### 4. Pantallas Requeridas (Mínimo Viable)

Deben coincidir con los flujos diseñados en DIN:

- **Auth Screen:** Login/Registro (con validación de campos).
- **Home/Listado:** RecyclerView/Lista obteniendo datos reales del servidor.
- **Detalle:** Pantalla para ver la información extendida de un elemento.
- **Edición/Creación:** Formulario para enviar datos al servidor (POST/PUT).

> [!NOTE]
> A partir de ahí si queréis añadir más funcionalidades, pantallas, caché con base de datos local offline-first, etc. sois libres de hacerlo. Todo eso es valorado muy positivamente en la evaluación.

### 🤖 Política sobre Inteligencia Artificial

Podéis apoyaros en el uso de asistentes de IA (ChatGPT, GitHub Copilot, etc.) para acelerar la escritura de código "boilerplate" o resolver dudas puntuales. **Sin embargo:**

- **Defensa oral:** Debéis ser capaces de explicar cada línea de código. Si la IA escribe algo que no entendéis, no lo incluyáis.
- **Calidad:** La IA comete errores. Vosotros sois responsables de que el código compile y siga las buenas prácticas.

### 📦 Entrega

- Repositorio de GitHub con el código fuente (bien organizado, con `.gitignore` adecuado).
- APK compilado (release o debug) funcional.
- Breve vídeo o capturas demostrando la funcionalidad.

### ✅ Criterios de evaluación

> [!IMPORTANT]
> La aplicación debe cumplir los siguientes criterios para ser evaluada

**Requisitos mínimos (condición para ser evaluable):**

- La aplicación debe **compilar** y **ejecutarse** sin cierres al iniciar.
- Debe existir **consumo real de API REST** y **autenticación real con Firebase** (no se admite “app maqueta”).

**Penalización por “app zombie”:**

- Si la app es solo UI (pantallas pintadas) sin consumo real de API y/o sin Auth: **suspenso** (independientemente de lo “bonita” que sea).

| Bloque | Peso | Qué se valora (resumen) |
| :--- | :---: | :--- |
| **Funcionalidad core (API + Auth)** | **60%** | Login/registro y sesión con Firebase; listado desde API (GET); detalle y creación/edición (POST/PUT). Si una pantalla existe pero no conecta/persiste, puntúa 0 en esa parte. |
| **Implementación técnica** | **30%** | Retrofit + corrutinas/Flow, arquitectura (MVVM/clean o separación lógica), manejo de estados (loading/error), que no crashee sin internet. |
| **Fidelidad UI/UX** | **10%** | Respeto a guía de estilo de DIN, usabilidad básica y feedback (cargas, errores, validaciones). |
