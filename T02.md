## Kotlin Crash Course para Alumnos de Java

Kotlin es un lenguaje de programación desarrollado por JetBrains, moderno, conciso y seguro. Se ejecuta en la Java Virtual Machine (JVM). Su diseño busca mejorar la productividad del desarrollador y reducir los errores comunes asociados con la programación en Java. 

Kotlin apareció oficialmente (primera versión estable) en 2016, aunque su desarrollo comenzó en 2010 y se presentó públicamente en 2011. Este lenguaje fue creado por JetBrains, la empresa detrás del popular IDE IntelliJ IDEA, con un objetivo claro: evolucionar Java manteniendo su compatibilidad.

### 1. La función `main()`

En **Java**, estamos acostumbrados a la verbosidad (sí, este adjetivo existe en castellano). Además, todo tiene que vivir dentro de una clase, lo que hace que incluso un simple "Hola Mundo" requiera varias líneas de código. *Nota*: sé que esto mejora en Java 25:

```java
public class Main {
    public static void main(String[] args) {
        System.out.println("Hola desde Java");
    }
}
```

En **Kotlin**, la entrada es mucho más directa. Es una función de nivel superior (no necesita una clase que la contenga), lo que reduce el código "boilerplate" o repetitivo.

```kotlin
fun main() {
    println("¡Hola desde Kotlin!")
}
```

Esta filosofía es troncal al lenguaje Kotlin, que busca ser **conciso y pragmático**. Menos código para hacer lo mismo significa menos errores y más legibilidad. En general a la gente que viene de Java le encanta este enfoque.

Otros ejemplos de esta concisión del lenguaje:

- **Lambdas**

```java
// Java 7 o anterior: clase anónima
boton.setOnClickListener(new View.OnClickListener() {
    @Override
    public void onClick(View v) {
        // Acción al hacer clic
    }
});

// Desde Java 8: lambda
boton.setOnClickListener(v -> {
    // Acción al hacer clic
});
```

```kotlin
boton.setOnClickListener {
    // Acción al hacer clic
}
```

- **Definición de clases**

```java
public class Persona {

    // Atributos
    private String nombre;
    private int edad;

    // Constructor
    public Persona(String nombre, int edad) {
        this.nombre = nombre;
        this.edad = edad;
    }
  
    // Getters y Setters
    public String getNombre() {
        return nombre;
    }
    public int getEdad() {
        return edad;
    }
    public void setNombre(String nombre) {
        this.nombre = nombre;
    }
    public void setEdad(int edad) {
        this.edad = edad;
    }

    // toString, hashCode, equals, copy...

    //Resto de métodos...
}
```

```kotlin
data class Persona(var nombre: String, var edad: Int)
// Resto de métodos
```
Ya iremos entrando al detalle, la idea es transmitiros que Kotlin es conciso como Python, pero con la seguridad de tipos de Java. Esto es un gran punto a favor para los que venimos de Java y queremos escribir código más limpio y mantenible.

> [!NOTE]
> Desde Java 16 existen los `record` (`record Persona(String nombre, int edad) {}`), que acortan mucho este código. Aun así no son equivalentes: un `record` es siempre inmutable (no tiene setters) y no tiene `copy()`. La `data class` de Kotlin es mutable o no según uses `var` o `val`, y lo recomendable es preferir `val`.

### 2. Sacando información por pantalla: `print()` y `println()`

De nuevo, la simpleza es la clave. En Java imprimíamos por pantalla usando `System.out.println()`. Esto son tres niveles de jerarquía para algo tan básico como mostrar texto. Clase `System`, objeto `out` (salida estándar), método `println()`.

- En **Kotlin**, las funciones `print()` y `println()` están disponibles directamente.
- `println()` añade un salto de línea al final, mientras que `print()` no lo hace.

```kotlin
fun main() {
    print("Esto es una línea.")
    print(" Y esto sigue en la misma línea.")
    println() // Salto de línea explícito
    println("Esto aparece en una nueva línea.")
    println("Y esto en otra.")
}
```

En Kotlin, estas funciones forman parte de la librería estándar de Kotlin, que se importa por defecto en todos los ficheros `.kt`. Por eso nos ahorramos escribir `System.out...` cada vez. Sin duda una lección aprendida de esos 30 años de Java.

![Meme: una mano ignora la pastilla azul «aprender a depurar con DevTools» y se hunde en un montón de pastillas rojas «console.log()»](img/T02/meme-depurar-con-console-log.jpg)

**Nota:** En Android Studio, lo habitual es usar `Log.d(TAG, "Mensaje de depuración")` para depurar. Esto es **CLAVE** en los exámenes cuando no vemos por dónde se está rompiendo el código.

### 3. Nomenclatura: Naming Conventions

Normalmente el tema de la nomenclatura se pasa demasiado por alto, pero desde la experiencia personal en proyectos software, es lo primero que muchos miramos para saber si podemos esperar un código profesional y mantenible o un circo de los horrores. Si la gente no ha sido capaz de seguir unas simples convenciones de nombres, ¿cómo podemos confiar en que su código sea sólido y bien estructurado? Lo mismo sucede con las faltas de ortografía en la UI, generan desconfianza sobre la calidad del producto. ¿Si algo tan obvio se ha escapado de las pruebas, qué más puede estar mal?

Buena noticia: las convenciones son prácticamente idénticas a las de Java, lo que facilita la transición.

- **Clases e Interfaces:** `PascalCase` (ej. `MiClaseAdaptadora`).
- **Funciones y Variables:** `camelCase` (ej. `miVariable`, `calcularTotal()`).
- **Constantes:** `SCREAMING_SNAKE_CASE`, es decir, mayúsculas separadas por guiones bajos (ej. `const val MAX_INTENTOS = 3`).
- **Diferencia clave con Java ‼️:** En Java, cada clase pública tiene que ir en un fichero con su mismo nombre (`Persona.java`) y el compilador lo exige. En Kotlin, no: un fichero `.kt` puede contener varias clases y funciones y llamarse como quieras, y el paquete (ej. `package com.ies.proyecto`) **tampoco tiene por qué coincidir con la estructura de directorios**. Aun así, es una buena práctica mantener la coherencia (si un fichero contiene una sola clase, que se llame como ella). Normalmente de esto se encarga el IDE automáticamente, pero no está de más mencionarlo.

### 4. Manejo de Strings

Aquí es donde Kotlin empieza a brillar de verdad para los que vienen de Java. Esta parte era un dolor de muelas en Java y Kotlin lo hace mucho más sencillo e intuitivo, similar a las string templates de JavaScript o Python.

- **Strings Multilínea:** En Java, hasta la versión 15 crear un string multilínea era engorroso (`"línea1\n" + "línea2"`); desde Java 15 existen los *text blocks* con `"""`. En Kotlin se usan también las triples comillas `"""`, ¡igual que en Python! 🐍

    ```kotlin
    // Ideal para JSON, SQL, o cualquier texto largo como menús, mensajes de ayuda, etc.
    val miJson = """
    {
        "usuario": "Juan",
        "activo": true
    }
    """.trimIndent() // Quita la sangría común y las líneas en blanco del principio y del final
    println(miJson)
    ```

- **String Templates (Plantillas de Strings):** Mientras que en Java se concatena con `+` o se usa `String.format()`, Kotlin lo integra de forma nativa con el símbolo `$`.

    ```kotlin
    val nombre = "Ana"
    val edad = 28
    // En Java: String saludo = "Hola, me llamo " + nombre + " y tengo " + edad + " años.";
    // En Kotlin:
    val saludo = "Hola, me llamo $nombre y tengo $edad años."
    println(saludo)
    // Para expresiones más complejas, se usan llaves
    println("El año que viene, $nombre tendrá ${edad + 1} años.")
    ```

### 5. Mutabilidad: `val` vs. `var`

Este es un cambio de paradigma fundamental respecto a Java.

- `val` (de *value*): Se usa para declarar variables **inmutables** (solo lectura). Es el análogo al `final` de Java. Una vez asignado un valor, no se puede reasignar.

```kotlin
val nombre = "María"
// nombre = "Lucía" // Error de compilación: Val cannot be reassigned
// en Java sería: final String nombre = "María";
```

- `var` (de *variable*): Se usa para variables **mutables**, cuyo valor puede cambiar.

```kotlin
var contador = 0
contador += 1 // Correcto
```

```kotlin
val nombreCompleto = "Carlos" // No se puede reasignar, pero el objeto al que apunta podría ser mutable. En cualquier caso, String es inmutable en Kotlin (igual que en Java).
var edadActual = 22
// nombreCompleto = "Luis" // Error de compilación: Val cannot be reassigned
edadActual = 23 // Correcto
```

En la medida de lo posible utilizar `val` como buena práctica para prevenir errores. Si intentamos reasignar un `val`, el compilador nos avisará inmediatamente.

### 6. Sistema de tipos e inferencia

Este es un tema que merece un poco más de atención porque hay importantes diferencias entre los lenguajes de programación. Si bien en este curso nos centraremos en Kotlin, no es raro que a lo largo de vuestra carrera profesional os toque trabajar con distintos lenguajes, frameworks y paradigmas (ya sabéis... adaptarse o morir).

[Popularidad de los lenguajes de programación](https://www.youtube.com/watch?v=ZTPrbAKmcdo)

#### Tipado dinámico vs. estático

- **Dinámico** → El tipo se asocia al valor y se comprueba **en tiempo de ejecución**. Una variable puede cambiar de tipo durante la ejecución.  
  Ej.: Python:  

  ```python
  x = 5       # int
  x = "hola"  # str 
  ```

- **Estático** → El tipo se asocia a la variable y se comprueba **en tiempo de compilación**. Una variable no puede cambiar de tipo: si le asignas un valor de otro tipo, el compilador da error.  
  Ej.: Kotlin / Java:  

  ```kotlin
  var x: Int = 5
  x = "hola" // ❌ Error de compilación
  ```

-----

#### Tipado fuerte vs. débil

- **Fuerte** → No permite mezclar tipos *incompatibles* sin conversión explícita.  
  Ej.: Python y Kotlin:  

  ```python
  5 + "7"  # ❌ TypeError
  ```

- **Débil** → Hace conversiones implícitas para que la operación funcione.  
  Ej.: JavaScript:  

  ```javascript
  "5" * 2 // 10 (convierte implícitamente el string a número)
  "5" - 2 // 3
  ```

> [!NOTE]
> `5 + "7"` → `"57"` **no** sirve como ejemplo de tipado débil: Java da exactamente lo mismo, y en Kotlin `"7" + 5` también compila y da `"75"`. Ahí no hay conversión "a escondidas", sino una regla explícita del lenguaje: `+` con un `String` significa concatenar.

El caso de JavaScript es paradigmático por la cantidad de comportamientos inesperados. Midudev hace frecuentemente tests en Instagram sobre esto y son complicados si no estás muy en el mindset de JavaScript.

-----

**🔍 Cuadro resumen:**

| Lenguaje  | Dinámico/Estático | Fuerte/Débil | ¿Inferencia de tipos? |
|-----------|-------------------|--------------|-----------------------|
| **Python** | Dinámico          | Fuerte       | No aplica (el tipo va con el valor, no con la variable) |
| **JavaScript** | Dinámico      | Débil        | No aplica (el tipo va con el valor, no con la variable) |
| **Kotlin** | Estático          | Fuerte       | Sí (muy potente con `val`/`var`) |
| **Java**   | Estático          | Fuerte       | Sí, desde Java 10 con `var` (antes no) |

Ojo que todavía mucho code legacy de Java es de Java 8 o anterior, donde no existía `var` y la inferencia de tipos era muy limitada. Muchos venimos de ahí y arrastramos esa fosilización mental.

```kotlin
// Inferencia de tipos (el compilador sabe que son String e Int respectivamente)
val mensaje = "Bienvenida a PMDM"
var anno = 2026

// Tipado explícito (a veces necesario o preferible por claridad)
val notaFinal: Double = 9.5
var profesor: String = "Profesor Sergio"
```

En Kotlin, los literales enteros son `Int` por defecto y los literales con decimales son `Double` por defecto.  

```kotlin
val numeroEntero = 42        // Int por defecto
val numeroDecimal = 3.14     // Double por defecto
```

Si queremos `Long` o `Float`, debemos indicarlo explícitamente, ya sea con anotación de tipo o usando los sufijos `L` (para `Long`) o `f`/`F` (para `Float`).  

En el caso de `Byte` y `Short`, no existen sufijos de literal, por lo que siempre hay que indicarlos de forma explícita mediante anotación de tipo o conversión (`toByte()`, `toShort()`).

Insistir en que la inferencia de tipos no hace que Kotlin sea de "tipado dinámico" como Python, ni "débilmente tipado" como JavaScript. El tipo sigue estando ahí, es fijo y se comprueba en compilación, lo que nos da la seguridad de Java con la verbosidad reducida de un lenguaje de scripting.

### 7. Flujo de Entrada y Salida (I/O)

Mientras que en **Java** se necesita un objeto `Scanner` para leer desde la consola, Kotlin lo simplifica enormemente.

En **Kotlin**, la función principal para leer una línea de texto desde la entrada estándar es `readln()`. Es importante destacar que `readln()` siempre devuelve un `String`: si lo que queremos es un número, tendremos que convertirlo (lo veremos en la [sección 12](#12-conversión-de-tipos)).

```kotlin
fun main() {
    println("Por favor, introduce tu nombre:")
    val nombre = readln()

    println("Hola, $nombre. Ahora, introduce tu edad:")
    val edadString = readln()

    // Adelanto de la conversión de tipos. Si no escribe un número, lanza NumberFormatException
    val edad = edadString.toInt()

    println("Gracias. Has confirmado que tienes $edad años.")
}
```

> [!NOTE]
> Antes de Kotlin 1.6 se usaba `readLine()`, que devuelve un `String?` (un String que puede ser nulo). Sigue existiendo, igual que su equivalente moderno `readlnOrNull()`. La diferencia con `readln()` está en qué pasa cuando no hay ninguna línea que leer: `readln()` lanza una excepción, mientras que `readLine()` y `readlnOrNull()` devuelven `null` y te obligan a manejar ese caso. Esta forma de tratar los nulos es una de las mayores ventajas de Kotlin sobre Java para evitar el famoso `NullPointerException`, y la veremos en detalle en la [sección 14](#14-anulabilidad-y-seguridad-de-nulos).

### 8. Variables `val` y `var` Profundizando

Ya introdujimos `val` y `var`, pero un punto clave que confunde a los que vienen de Java es la diferencia entre **referencia inmutable y objeto inmutable**.

Un `val` declara una **referencia inmutable**, similar a `final` en Java. Esto significa que no puedes reasignar la variable para que apunte a otro objeto, pero si el objeto en sí es mutable (como una lista mutable), **su contenido sí puede cambiar**. Para poder ver esto me toca adelantarme un poco al tema de las colecciones con el código de abajo.

```kotlin
// La lista es una referencia inmutable (val)
val colores = mutableListOf("rojo", "verde", "azul")

// Esto daría un error de compilación, no podemos reasignar la variable 'colores'
// colores = mutableListOf("amarillo", "naranja")

// Pero sí podemos modificar el contenido del objeto al que apunta
colores.add("amarillo") // ¡Esto es totalmente válido!
println(colores) // Imprime [rojo, verde, azul, amarillo]
```

### 10. Tipos de Datos: ¿Primitivos o no?

Una de las diferencias más elegantes y simplificadoras de Kotlin respecto a Java es la siguiente: En **Java**, existen tipos primitivos (`int`, `double`, `boolean`) y sus clases envoltorio (wrapper) (`Integer`, `Double`, `Boolean`). En **Kotlin**, **todo es un objeto**. No hay distinción a nivel de código entre primitivos y sus envoltorios; usamos `Int`, `Double`, `Boolean`, etc., directamente.

```kotlin
val numero: Int = 42
// Podemos llamar a métodos directamente sobre el número, porque es un objeto.
val numeroComoString: String = numero.toString()
```

Eso sí, esto es solo a nivel de código. Por debajo, el compilador sigue usando los primitivos de la JVM (`int`, `double`…) siempre que puede, porque son más eficientes. Solo recurre al envoltorio (`Integer`) cuando hace falta: por ejemplo, con tipos anulables (`Int?`) o dentro de colecciones genéricas (`List<Int>`).

### 11. Arrays y Strings

Ambos son fundamentales, y Kotlin ofrece mejoras de calidad de vida.

- **Strings:** Además de las plantillas y los strings multilínea, muchas operaciones son ahora propiedades en lugar de métodos. Por ejemplo, se usa `.length` en lugar del método `.length()` de Java. Se queda como en JavaScript.

```kotlin
val saludo = "Hola, Mundo"
println("La longitud es: ${saludo.length}") // .length es una propiedad
```

- **Arrays:** La sintaxis de creación es más limpia. Se usan funciones de librería como `arrayOf()` para crear arrays con elementos, o `IntArray()` / `DoubleArray()`, que por debajo son arrays de primitivos de la JVM (`int[]`, `double[]`) y, por tanto, más eficientes que un `Array<Int>`.

```kotlin
// En Java: String[] nombres = {"Juan", "Eva"};
val nombres = arrayOf("Juan", "Eva")

// En Java: int[] numeros = new int[5];
val numeros = IntArray(5) // Crea un array de 5 enteros, inicializados a 0

println(nombres[0]) // El acceso es igual, con corchetes
println(nombres.size) // ¡Ojo! El tamaño es .size, no .length como en Java
```

> [!NOTE]
> Fijate en el detalle, array usa `.size` y string usa `.length`.

### 12. Conversión de Tipos

Kotlin es más estricto que Java con las conversiones entre tipos numéricos.

En **Java**, algunas conversiones se realizan automáticamente. Por ejemplo, un `int` puede asignarse directamente a un `long` porque todos los valores posibles de `int` caben dentro de un `long`.

En **Kotlin esto no ocurre**: si tenemos una variable de un tipo numérico y queremos obtener otro tipo, debemos indicar la conversión explícitamente.

```kotlin
val miInt: Int = 100

// val miLong: Long = miInt    // ERROR

val miLong: Long = miInt.toLong()
val miDouble: Double = miInt.toDouble()
```
toByte
Kotlin proporciona funciones como:

```kotlin
toByte()
toShort()
toInt()
toLong()
toFloat()
toDouble()
```

Esto obliga a dejar claro en el código cuándo queremos cambiar la representación numérica de un valor.

Por ejemplo:

```kotlin
val edad: Int = 25
val edadComoLong: Long = edad.toLong()
```

Aunque un `Int` cabe perfectamente dentro de un `Long`, Kotlin **no realiza esa conversión automáticamente al asignar variables o pasar argumentos a funciones**.

#### Literales numéricos

Hay una excepción importante: los **literales** pueden adaptarse al tipo que espera el contexto.

```kotlin
val numero: Long = 100
```

Aquí `100` no es una variable de tipo `Int` que se esté convirtiendo a `Long`: es un literal cuyo tipo puede determinarse a partir del contexto.

Por eso esto funciona:

```kotlin
val a: Long = 100
```

pero esto no:

```kotlin
val a: Int = 100
val b: Long = a       // ERROR
```

y necesitamos:

```kotlin
val b: Long = a.toLong()
```

#### Operaciones entre distintos tipos numéricos

En las expresiones aritméticas sí podemos combinar algunos tipos numéricos:

```kotlin
val a = 1L + 3
val b = 3 + 3.0
```

En estos casos:

```text
a → Long
b → Double
```

Kotlin sabe qué operación debe realizar según los tipos de los operandos.

Eso no significa que después podamos guardar el resultado en cualquier tipo:

```kotlin
val x: Double = 3 + 3.0   // OK

// val y: Int = 3 + 3.0   // ERROR
```

El resultado de `3 + 3.0` es un `Double`, por lo que no puede asignarse directamente a un `Int`.

#### Convertir texto a número es otra cosa

También encontraremos expresiones como:

```kotlin
val texto: String = "42"
val numero: Int = texto.toInt()
```

Aunque también se llama `toInt()`, aquí estamos haciendo algo conceptualmente diferente: **interpretamos una cadena de caracteres como un número**.

Si el contenido no representa un entero válido:

```kotlin
val texto = "hola"
val numero = texto.toInt()
```

se produce una `NumberFormatException`.

Más adelante veremos `toIntOrNull()`, que permite realizar esta operación de forma segura aprovechando la anulabilidad de Kotlin.

> [!NOTE]
> **Convertir no es lo mismo que hacer casting.**
>
> Las funciones `toInt()`, `toLong()`, `toDouble()`, etc. **crean un valor del nuevo tipo**.
>
> El *casting*, en cambio, se realiza en Kotlin mediante `as` y sirve para tratar una referencia como otro tipo compatible:
>
> ```kotlin
> val obj: Any = "Hola"
> val texto: String = obj as String
> ```
>
> `as` **no convierte el contenido del objeto**.
>
> Por eso no podemos utilizarlo para transformar un `Int` en un `Long`:
>
> ```kotlin
> val numero: Any = 10
> val otro = numero as Long   // ClassCastException
> ```
>
> El objeto almacenado en `numero` sigue siendo un `Int`. Si queremos obtener un `Long`, debemos realizar una conversión:
>
> ```kotlin
> val otro = (numero as Int).toLong()
> ```

### 14. Anulabilidad y Seguridad de Nulos

En **Java**, cualquier variable de tipo objeto puede ser `null` por defecto. Si intentan usar un método o propiedad de una variable que es `null`, la aplicación se detiene bruscamente en tiempo de ejecución como el infame `NullPointerException` (NPE).

El creador de `null`, Tony Hoare, se refirió a su invención como su "error del billón (inglés) de dólares" por la incalculable cantidad de horas de depuración y errores en producción que ha causado a lo largo de los años. [Fuente](https://www.infoq.com/presentations/Null-References-The-Billion-Dollar-Mistake-Tony-Hoare/)

-----

#### La Solución de Kotlin: El Sistema de Tipos Nulables

Kotlin aborda este problema directamente desde su sistema de tipos. La regla fundamental es: **por defecto, las variables NO pueden ser nulas**. El propio compilador no te dejará asignar `null` a una variable normal.

Para permitir que una variable pueda contener `null`, debemos declararlo explícitamente añadiendo una interrogación (`?`) al final del tipo.

```kotlin
// TIPO NO NULABLE (por defecto)
var nombre: String = "IES Severo Ochoa"
// nombre = null  // ¡ERROR DE COMPILACIÓN! El compilador nos protege.

// TIPO NULABLE (explícito con ?)
var alias: String? = "El mejor instituto"
alias = null // ¡Correcto! Esta variable está diseñada para poder ser nula.
```

> [!NOTE]
> Es un cambio de paradigma importante con respecto a Java. En Java, se asume que algo *puede* ser nulo y es responsabilidad del programador recordarlo. En Kotlin, se asume que algo *nunca* es nulo, y si puede serlo, el compilador te **obliga** a manejar esa posibilidad.

-----

#### Herramientas para Manejar Nulos de Forma Segura 🛠️

Una vez que tienes una variable nulable (con `?`), el compilador no te dejará usarla directamente. Te obligará a usar una de estas herramientas para garantizar la seguridad.

##### **1. El Operador de Llamada Segura (`?.`)**

Es la forma más común y elegante. Ejecuta la acción (llamar a un método, acceder a una propiedad) solo si el objeto no es nulo. Si es nulo, toda la expresión devuelve `null` y la ejecución continúa sin fallar.

```kotlin
val instituto: String? = "IES Severo Ochoa"
println(instituto?.length) // Imprime 16

val institutoNulo: String? = null
println(institutoNulo?.length) // Imprime "null" en la consola, ¡pero no rompe la app!
```

##### **2. El Operador Elvis (`?:`)**

![Elvis Operator](img/T02/elvis_operator.webp)

Perfecto para proporcionar un valor por defecto cuando una variable es nula. Si la expresión a la izquierda del operador Elvis no es nula, se usa su valor; si es nula, se usa el valor de la derecha.

```kotlin
val nombreProfesor: String? = null
val nombreAMostrar = nombreProfesor ?: "Profesor Desconocido"
println(nombreAMostrar) // Imprime "Profesor Desconocido"

// Se puede encadenar con la llamada segura:
val longitud = nombreProfesor?.length ?: 0
println("La longitud del nombre es $longitud") // Imprime "La longitud del nombre es 0"
```

##### **3. El Operador de Aserción No Nula (`!!`)**

Esta es la opción más arriesgada y la que más se parece al comportamiento de Java. Le dice al compilador: "Te aseguro que esta variable no es nula aquí. Confía en mí y déjame usarla" **Trust me bro**. Si te equivocas y la variable es `null`, **la aplicación se romperá con un `java.lang.NullPointerException`**.

```kotlin
val direccion: String? = "Av. de la Unesco, s/n"
val longitud = direccion!!.length // Funciona porque no es nulo

val direccionNula: String? = null
// val longitudNula = direccionNula!!.length // ¡CRASH! Lanza una excepción.
```

El operador `!!` es lo que llamos un **code smell**, algo que pinta mal. Por lo general **evitad el operador `!!` siempre que sea posible**. Su uso es considerado una mala práctica y a menudo indica que la lógica del programa podría mejorarse usando llamadas seguras u operadores Elvis. Es una "salida de emergencia", no una herramienta de uso diario.

> [!NOTE]
> A mi me gusta llamarlo *hold my beer operator*, crédito a [https://stackoverflow.com/questions/47543386/what-is-the-name-of-kotlins-operator](https://stackoverflow.com/questions/47543386/what-is-the-name-of-kotlins-operator)

##### **4. `Smart Casts` (Conversiones Inteligentes)**

El compilador de Kotlin es lo suficientemente inteligente como para saber que si has comprobado que una variable no es nula, dentro de ese bloque de código, puede tratarla como si fuera no nulable, sin necesidad de operadores.

```kotlin
var email: String? = "info@iesseveroochoa.com"

if (email != null) {
    // Dentro de este 'if', el compilador sabe que 'email' no es nulo.
    // Podemos usarlo como un String normal, sin '?' ni '!!'.
    println("El email tiene ${email.length} caracteres.")
}
```

> [!NOTE]
> No hay que confundir el operador elvis `?:` con el valor por defecto de un parámetro.

### 16. Sentencia if

La sentencia `if` en Kotlin es muy similar a la de Java.

La sintaxis básica es:

```kotlin
if(expresion){
    // Acciones si se cumple expresion
}else if (expresion_alt1){
    // Acciones si se cumple condición alternativa 1
}else{
    // Acciones si nada se cumple

```

Hasta aquí nada nuevo. También tenemos el `if` como expresión (el if ternario de Java), que devuelve un valor:

val attack = if (armor <= 0) 10 else 5

También se puede usar el `if` como expresión de varias líneas, con el `else` al final:

```kotlin
val attack = if (armor <= 0) {
    println("¡Ataque crítico!")
    10
} else {
    println("Ataque normal")
    5
}
```

### 17. Rangos

Los rangos son una forma elegante de representar un conjunto de valores consecutivos. Se crean usando el operador `..` y se pueden usar en bucles `for`, comprobaciones de pertenencia y más.

```kotlin
println(0..5) // Imprime 0..5. No es un array, es un rango de valores.
```

Se puede comprobar si un valor está dentro (pertenencia) de un rango usando `in`:

```kotlin
val numero = 3
if (numero in 1..5) {
    println("$numero está entre 1 y 5")
} else {
    println("$numero no está entre 1 y 5")
}
```

También está la sintaxis con el operador rangeTo

```kotlin
val rango = 1.rangeTo(5) // Lo mismo que 1..5
```

Si no quieres incluir el límite superior, puedes usar `until`. Aprovechamos para verlo con el bucle `for`:

```kotlin
for (i in 1 until 5) { // i tomará los valores 1, 2, 3, 4
    println(i)
}
```

También tenemos:
- `downTo` para contar hacia atrás: `for(i in 30 downTo 20)`
- `step` para saltos: `for(i in 1..10 step 2)`

### 18. Sentencia for

La sentencia `for` en Kotlin es similar a la de Java en intención, pero **más expresiva y más cercana a iteradores** que a contadores clásicos. Esta es una de las cuestiones por las que suelo decir que Kotlin me evoca al motor de Java con el chasis de Python.

La sintaxis básica es:

```kotlin
for (item in coleccion) {
    // Acciones con cada elemento
}
```

El `for` **siempre itera sobre un rango, colección o cualquier objeto iterable**. No existe el `for(int i = 0; i < n; i++)` de Java.

---

#### Iterar rangos numéricos

```kotlin
for (i in 0..10) { // Incluye el 10
    println(i)
}
```

- `0..10` incluye ambos extremos.  
- Para excluir el final: `0 until 10`.

También puedes controlar el paso:

```kotlin
for (i in 0..10 step 2) println(i)
```

Y recorrer hacia atrás:

```kotlin
for (i in 10 downTo 0) println(i)
```

---

#### Iterar colecciones

```kotlin
val nombres = listOf("Ana", "Luis", "Marta")

for (nombre in nombres) {
    println(nombre)
}
```

Si necesitas índice y valor:

```kotlin
for ((index, value) in nombres.withIndex()) {
    println("$index -> $value")
}
```



---

#### El `for` es azúcar sintáctico

Como hemos dicho, al final por debajo tenemos *Java bytecode* corriendo en una JVM. Internamente, Kotlin traduce el `for` a:

- Obtener un **iterator**.
- Llamar a `hasNext()`.
- Llamar a `next()`.

Por eso funciona con cualquier tipo que implemente `iterator()`.

---

#### No existe el `for` clásico de Java

Este:

```java
for (int i = 0; i < n; i++) { ... }
```

En Kotlin se expresa con rangos:

```kotlin
for (i in 0 until n) { ... }
```

Otra cuestión importante es que, a la hora de modificar una colección mientras la recorres, debes tener cuidado. El comportamiento es el mismo que en Java, y no por casualidad: `mutableListOf` te devuelve un `ArrayList` de toda la vida, con su mismo iterador. Lo habitual es que salte un `ConcurrentModificationException`:

```kotlin
val nombres = mutableListOf("Ana", "Luis", "Marta")

for (nombre in nombres) {
    if (nombre == "Ana") {
        nombres.remove(nombre)  // ConcurrentModificationException en la siguiente vuelta
    }
}
```

Pero ojo, que **no siempre salta**, y ahí está el verdadero peligro. Si borras el penúltimo elemento, el bucle termina sin protestar... y saltándose el último (sí, muy loco):

```kotlin
val nombres = mutableListOf("Ana", "Luis", "Marta")

for (nombre in nombres) {
    if (nombre == "Luis") {
        nombres.remove(nombre)  // No falla: simplemente "Marta" nunca se visita
    }
}
```

> [!WARNING]
> El motivo está en cómo está escrito el iterador de `ArrayList`: la comprobación de "me han tocado la lista por debajo" vive en `next()`, no en `hasNext()`, y `hasNext()` es simplemente `cursor != size`. Después de visitar `"Luis"` el cursor vale 2; al borrarlo, `size` pasa a valer 2 también, así que `hasNext()` devuelve `false`, el bucle acaba y nadie llega a comprobar nada.
>
> Que no salte la excepción es peor noticia, no mejor: una excepción te avisa en el acto, mientras que un elemento saltado en silencio se te cuela hasta producción.

Si de verdad necesitas borrar mientras recorres, usa un iterador explícito como en Java:

```kotlin
val lista = mutableListOf(1, 2, 3, 4, 5)
val it = lista.iterator()

while (it.hasNext()) {
    val n = it.next()
    if (n % 2 == 0) {
        it.remove()  // Aquí sí, el iterador se encarga de mantener la cuenta
    }
}
```

Todo sea dicho, en Kotlin rara vez vas a escribir eso. Lo idiomático es no tocar la colección mientras la recorres, sino producir una nueva con funciones de orden superior (`filter`, `map`...) o usar `removeAll` / `retainAll`, que ya hacen el trabajo sucio por ti:

```kotlin
val pares = lista.filter { it % 2 == 0 }   // nueva lista, la original intacta: 2 y 4
lista.removeAll { it % 2 == 0 }            // modifica lista, sin iteradores a mano
```

### 19. Sentencia when

La sentencia when es una especie de `switch` mejorado. Permite evaluar una expresión y ejecutar bloques de código según el valor de esa expresión. Esto es muy útil en Jetpack Compose, donde se usa mucho para renderizar diferentes componentes según el estado de la UI. También es una estructura de control que, en el perímetro del desarrollo Android, suele combinarse con las *sealed classes* (que veremos más adelante), para no tener que poner un `else` ficticio.

Las entradas del `when` siguen un patrón un poco particular:
`condition -> cuerpo`

Las condiciones pueden ser: expresiones, comprobaciones de rangos y comprobaciones de tipos. Si encuentra una coincidencia ejecuta la entrada correspondiente a esa condición y sale del `when`. Si no encuentra ninguna coincidencia, ejecuta el bloque `else` (si existe).

A modo de ejemplo, este código muestra cómo usar `when` para decidir si continuar o salir según la entrada del usuario (hardcodeada en este caso):

```kotlin
fun main() {
    val keepPlaying  = 'y'

    when (keepPlaying) {
        'y' -> println("Continuar")
        'n' -> println("Salir")
        else -> println("Opción no válida")
    }
}

```

Fíjate que a diferencia del `switch` de Java, el `when` no necesita `break` al final de cada caso. Esto es porque el `when` **no "cae" al siguiente caso**: una vez que encuentra una coincidencia, ejecuta ese bloque y sale automáticamente.

También permite comprobar múltiples valores en una sola entrada, por ejemplo para calcular que día de la semana es según un número:

```kotlin
fun main() {
    val dayOfWeek = 3

    when (dayOfWeek) {
        1, 2, 3, 4, 5 -> println("Día laborable")
        6, 7 -> println("Fin de semana")
        else -> println("Número de día no válido")
    }
}
```

Alternativamente se pueden usar expresiones como condiciones:

```kotlin
fun main() {
    val dayOfWeek = 3

    when {
        dayOfWeek > 0 && dayOfWeek < 6 -> println("Día laborable")  //Condiciones lógicas
        dayOfWeek in 6..7 -> println("Fin de semana")               //Pertenencia a rango
        else -> println("Número de día no válido")
    }
}
```

Nótese que para la pertenencia a rangos tenemos tanto `in` como `!in` para comprobar que un valor **no** pertenece a un rango.

Para comparar tipos con `when`, podemos usar `is` y `!is`. El siguiente ejemplo básicamente comprueba el tipo concreto de la variable `obj` en tiempo de ejecución y actúa en consecuencia. Esto es muy útil cuando trabajamos con tipos genéricos o `Any` (el supertipo de todos los tipos no nulos en Kotlin):

```kotlin
fun main() {
    val obj: Any = "Hola"  
 
    when (obj) {  // con 3 detectaría Int, con 3.0 detectaría desconocido el when
        is String -> println("Es un String de longitud ${obj.length}")
        is Int -> println("Es un Int con valor $obj")
        else -> println("Tipo desconocido")
    }
}
```

Aquí un ejemplo en el que usamos `when` como si fuese un `if`:

```kotlin
fun main() {
    val number = 5

    val result = when {
        number < 0 -> "Negativo"
        number == 0 -> "Cero"
        number % 2 == 0 -> "Par Positivo"
        else -> "Impar Positivo"
    }

    println("El número $number es $result")
}
```
Dentro del `when` podemos declarar una variable que solo será visible dentro de ese bloque. Esto es útil para evitar recalcular valores o para mantener el código más limpio.

```kotlin
fun calculateDamage(attackPower: Int): Int {
    // Simula un cálculo de daño basado en el poder de ataque
    return attackPower * 2// Por ejemplo, el daño es el 200% del poder de ataque
}

fun main() {
    val attackPower = 75

    when (val damage = calculateDamage(attackPower)) {
        in 0..20 -> println("Daño bajo: $damage")
        in 21..50 -> println("Daño medio: $damage")
        else -> println("Daño alto: $damage")
    }
}
```

Por último, el `when` también puede usarse como expresión que devuelve un valor, similar al `if` como expresión. Esto es útil para asignar valores a variables basadas en múltiples condiciones.

```kotlin
fun main() {
    val score = 85

    val grade = when {
        score >= 90 -> "A"
        score >= 80 -> "B"
        score >= 70 -> "C"
        score >= 60 -> "D"
        else -> "F"
    }

    println("La calificación es: $grade")
}
```

Y en su versión oneliner 

```kotlin
fun calculateGrade(score: Int): String = when {
    score >= 90 -> "A"
    score >= 80 -> "B"
    score >= 70 -> "C"
    score >= 60 -> "D"
    else -> "F"
}

fun main() {
    val score = 85
    val grade = calculateGrade(score)
    println("La calificación es: $grade")
}
```

### 22. Funciones

A esta altura ya hemos visto, inevitablemente, varias funciones. En Kotlin, las funciones se definen con la palabra clave `fun`, seguida del nombre de la función, los parámetros entre paréntesis y el tipo de retorno después de dos puntos. Si la función no retorna nada, podemos omitir el tipo de retorno o usar `Unit`.

La sintaxis básica es:

```kotlin
fun nombreDeLaFuncion(parametro1: Tipo1, parametro2: Tipo2): TipoRetorno {
    // Cuerpo de la función
    return valor
}
```

Para llamar a un función, simplemente usamos su nombre y pasamos los argumentos necesarios:

```kotlin
fun main() {
    val resultado = nombreDeLaFuncion(arg1, arg2)
    println(resultado)
}
```

Como hemos comentado, el tipo de retorno equivalente al `void` de Java es `Unit`. Si una función no retorna nada, podemos omitir el tipo de retorno o usar `Unit` explícitamente:

```kotlin
fun funcionSinRetorno() { //Esto es lo mismo que fun funcionSinRetorno(): Unit {
    println("Esta función no retorna nada")
}
```

Las funciones pueden tener parámetros con valores por defecto, lo que permite llamarlas sin necesidad de pasar todos los argumentos. Esta es la solución de Kotlin para evitar la sobrecarga (*overload*) de funciones que se ve en Java:

```kotlin
fun saludar(nombre: String = "Mundo") {
    println("Hola, $nombre!")
}

fun main() {
    saludar() // Imprime "Hola, Mundo!"
    saludar("Kotlin") // Imprime "Hola,
}
```

Los parámtros pueden llamarse de manera posicional (por orden) o por nombre, lo que mejora la legibilidad y permite omitir algunos parámetros si tienen valores por defecto:

```kotlin
fun crearUsuario(nombre: String, edad: Int = 18, ciudad: String = "Desconocida") {
    println("Usuario: $nombre, Edad: $edad, Ciudad: $ciudad")
}

fun main() {
    crearUsuario("Alice") // Imprime "Usuario: Alice, Edad: 18, Ciudad: Desconocida"
    crearUsuario("Bob", 25) // Imprime "Usuario: Bob, Edad: 25, Ciudad: Desconocida"
    crearUsuario("Charlie", ciudad = "Madrid") // Imprime "Usuario: Charlie, Edad: 18, Ciudad: Madrid"
    crearUsuario(
        nombre = "Sergio",
        ciudad = "Elche",
        edad = 35
    ) // Imprime "Usuario: Sergio, Edad: 35, Ciudad: Elche". Fijate que usando parámetros con nombre, podemos cambiar el orden de los argumentos.
}
```

Las funciones también pueden ser **anidadas**. Esto significa que podemos definir una función dentro de otra función. La función interna solo es accesible desde la función externa, lo que permite encapsular lógica y mantener el código más organizado:

```kotlin
fun funcionExterna() {
    println("Esta es la función externa")

    fun funcionInterna() {
        println("Esta es la función interna")
    }

    funcionInterna() // Llamada a la función interna desde la externa
}

fun main() {
    //funcionExterna().funcionInterna() // Esto daría error, ya que la función interna no es accesible desde aquí
    //funcionInterna() // Esto daría error, ya que la función interna no es accesible desde aquí
    funcionExterna()
}
```

A veces necesitamos que una función pueda recibir un número variable de argumentos. En Kotlin, esto se logra usando el modificador `vararg`. Esto permite pasar cero o más argumentos del mismo tipo a la función. Dentro de la función, los argumentos se tratan como un array.

```kotlin
fun sumarNumeros(vararg numeros: Int): Int {
    var suma = 0
    for (numero in numeros) {
        suma += numero
    }
    return suma
}

fun main() {
    val resultado1 = sumarNumeros(1, 2, 3) // Suma de 3 números
    println("Resultado 1: $resultado1") // Imprime "Resultado 1: 6"

    val resultado2 = sumarNumeros(10, 20, 30, 40) // Suma de 4 números
    println("Resultado 2: $resultado2") // Imprime "Resultado 2: 100"

    val resultado3 = sumarNumeros() // Sin argumentos
    println("Resultado 3: $resultado3") // Imprime "Resultado 3: 0"
}
```

Comentar también el uso del *spread operator* (`*`) para pasar un array a una función que recibe `vararg`. Retomando el ejemplo anterior:

```kotlin
fun main() {
    val numerosArray = intArrayOf(5, 10, 15)
    // val resultado = sumarNumeros(numerosArray) // Esto da error. sumarNumeros espera vararg Int, no un array de Int.
    val resultado = sumarNumeros(*numerosArray) // Usando el spread operator desempaquetamos el array en n elementos individuales
    println("Resultado con array: $resultado") // Imprime "Resultado con array: 30"
}
```

**Ampliación**: diferencia entre `Nothing`, `Unit` y `null` en Kotlin.

En Java, los métodos que no devuelven nada se declaran con `void`. En Kotlin, el equivalente conceptual es `Unit`, pero con una diferencia importante: **`Unit` es un tipo real y tiene un único valor posible**, también llamado `Unit`. Esto permite usarlo en expresiones y en genéricos, cosa que `void` no permite.

Por otro lado, `Nothing` es un tipo especial que indica que una función **nunca retorna**. Es el *tipo inferior* del sistema de tipos de Kotlin: no tiene valores y es subtipo de todos los tipos. Se usa en funciones que siempre lanzan una excepción, nunca terminan o representan código imposible.

Ejemplos:

```kotlin
fun funcionQueNoRetornaNada(): Unit {
    println("Esta función retorna Unit, aunque no aporta información útil")
}

fun funcionQueNuncaRetorna(): Nothing {
    throw Exception("Esta función nunca retorna, lanza una excepción")
}
```

Finalmente, no debemos confundir ninguna de estas funciones con una función que retorna `null`. En Kotlin, `null` es **un valor**, no un tipo. Solo puede aparecer en tipos anulables (`T?`). Por ejemplo, una función que puede devolver `null` tendría un tipo como `String?` o `Int?`, dependiendo del valor esperado.

Por otra parte tenemos el tipo `Any`, que es el supertipo de todos los tipos no nulos. Es decir, cualquier tipo que no sea anulable (`T`) es un subtipo de `Any`. Por ejemplo, `String` y `Int` son subtipos de `Any`, pero `String?` y `Int?` no lo son.

Resumen rápido de tipos *especiales* en Kotlin:

- **Unit** → tipo con un único valor (`Unit`). Funciones que retornan pero sin información útil.  
- **Nothing** → tipo sin valores. Funciones que nunca retornan.  
- **null** → valor que pertenece a tipos anulables (`T?`). No es un tipo.
- **Any** → supertipo de todos los tipos no nulos. No incluye `null`, para eso tenemos `Any?`.

### 27. Lambdas en Kotlin

**Programación Funcional**: Kotlin es un lenguaje con un fuerte enfoque en la programación funcional, lo que significa que las funciones son tratadas como ciudadanos de primera clase. A diferencia de Java (antes de la versión 8), en Kotlin las funciones no están atadas a las clases; pueden ser almacenadas en variables, pasadas como argumentos a otras funciones y devueltas como resultados. Este enfoque permite escribir un código más expresivo, conciso y modular.

El corazón de la programación funcional en Kotlin son las **expresiones lambda**. Una lambda es, esencialmente, una función anónima (sin nombre) que podemos tratar como un valor.

Antes de sumergirnos en la práctica, es fundamental entender la teoría. 

#### Sintaxis Básica de una Lambda

Una lambda se define entre llaves `{}`. A la izquierda de una flecha `->` se declaran los parámetros, y a la derecha está el cuerpo de la función. El valor de la última expresión en el cuerpo es lo que la lambda devuelve. Es muy parecido a las lambdas de JavaScript, aunque aquí para empezar usamos una flecha `->` en lugar de la fat arrow `=>`.

Esta lambda, por ejemplo, recibe dos parámetros enteros `s` y `t`, los suma, multiplica el resultado por 2 y lo devuelve.

```kotlin
fun main() {
    val miLambda: (Int, Int) -> Int = { s, t -> (s + t) * 2 }
    val resultado = miLambda(3, 4) // resultado será 14
    println("Resultado: $resultado")
}
```

Toma como referencia este lambda porque en este se especifican los tipos de los parámetros y el tipo de retorno. Esto es útil para que el compilador pueda inferir correctamente los tipos y para que otros desarrolladores comprendan mejor la intención del código aunque muchas veces se omite.

Aunque similar a los one-liners, las lambdas son más flexibles y se pueden pasar como argumentos a otras funciones, lo que permite un estilo de programación más funcional. Por suerte o por desgracia, esto es fundamental en Jetpack Compose, donde se usan lambdas para manejar eventos de UI y para definir la lógica de renderizado de componentes.

Por ejemplo pulsar un botón en Compose se hace pasando una lambda al parámetro `onClick` que veremos, similar a como ocurre en la programación web con JavaScript. La explicación es que los eventos de UI son asíncronos y no sabemos cuándo ocurrirán, así que necesitamos pasar una función (lambda) que se ejecute cuando el evento suceda (callback).

Aquí tienes algunos ejemplos para ilustrar la sintaxis:

| Expresión Lambda | Descripción |
| ---- | ---- |
| `{ println("Mensaje") }` | Llama al método `println`. No devuelve nada (`Unit`). |
| `{"Hola, mundo!"}` | Devuelve el `String` "Hola, mundo!". |
| `{ x: Int, y: Int -> x + y }` | Suma dos enteros pasados como parámetro. Se especifican los tipos de los parámetros y se omite (infiere) el tipo de retorno. |
| `{ x, y -> x + y }` | Suma dos valores. El tipo se infiere del contexto. A diferencia de la anterior, esta te valdría para sumar un par de `Double` como `2.0` y `3.0` |
| `{ x -> x * 2 }` | Multiplica un parámetro por dos. |
| `{ it * 2 }` | Si solo hay un parámetro, podemos usar `it` por defecto. Lo mismo que la anterior pero más conciso. |
| `{ _ , y -> y + 2 }` | El guion bajo `_` indica un parámetro que no usamos. Habitualmente para ajustarnos a una firma de función. |

#### Funciones de Orden Superior

Las lambdas cobran todo su sentido cuando se usan con **funciones de orden superior**, que son funciones que aceptan otras funciones como parámetros o las devuelven como resultado.

**Ejemplo:**
Imagina que queremos crear una función genérica que aplique una operación a cada elemento de una lista.

```kotlin
// Esta función de orden superior recibe una lista, un valor y una función (lambda)
fun opera(lista: List<Int>, valor: Int, funcion: (Int, Int) -> Int): List<Int> {
    val result = mutableListOf<Int>()
    for (item in lista) {
        // Ejecutamos la función pasada como parámetro
        result.add(funcion(item, valor))
    }
    return result
}
```
Y aquí surge la pregunta natural: ¿qué le pasamos exactamente a `funcion`?

La opción más directa es una función que ya tengamos escrita, usando el **operador de referencia** `::`:

```kotlin
fun multiplica(x: Int, y: Int): Int = x * y

val lista: List<Int> = listOf(2, 4, 5, 7)
val multiplicada = opera(lista, 7, ::multiplica) // [14, 28, 35, 49]
```

Fíjate bien en la diferencia, porque es el salto conceptual que más cuesta:

- `multiplica(2, 7)` **ejecuta** la función y obtiene un `14`.
- `::multiplica` **no la ejecuta**: entrega una referencia a la función para que `opera` la invoque ella misma con cada elemento.

Un matiz de vocabulario: `::multiplica` es una **referencia a función**, no una lambda. Ambas sirven para aportar el comportamiento que `opera` necesita, pero la documentación oficial de Kotlin las distingue y conviene que uses bien el término.

> [!TIP]
> Con una referencia, los argumentos entran **en el orden en que declaraste la función**, y no puedes adaptarlos. Con una lambda decides qué hacer con ellos dentro del cuerpo. Con `multiplica` no se nota, porque multiplicar es conmutativo, pero con una resta sí:
>
> ```kotlin
> fun resta(x: Int, y: Int): Int = x - y
>
> opera(lista, 3, ::resta)          // item - valor  →  [-1, 1, 2, 4]
> opera(lista, 3) { x, y -> y - x } // valor - item  →  [1, -1, -2, -4]
> ```
>
> En cuanto necesites invertir el orden, ignorar un parámetro o fijar uno de ellos, te toca lambda.

Ahora bien, muchas veces la operación es tan simple que no merece una función con nombre. Para eso están las lambdas: escribimos el comportamiento ahí mismo.

```kotlin
// El mismo resultado, pero con el comportamiento escrito en el momento
val multiplicada2 = opera(lista, 7, { x, y -> x * y }) // [14, 28, 35, 49]
```

Kotlin nos ofrece un "azúcar sintáctico" para hacer esto aún más legible: si la lambda es el último parámetro de una función, podemos sacarla fuera de los paréntesis.

```kotlin
// La misma llamada, pero más idiomática en Kotlin
val multiplicada = opera(lista, 7) { x, y -> x * y }

// Y ahora la usamos para sumar 3
val sumada = opera(lista, 3) { x, y -> x + y } // [5, 7, 8, 10]
```

#### Parámetro único: `it`

Para hacer el código aún más conciso, si una lambda tiene un solo parámetro, Kotlin nos permite omitir su declaración y referirnos a él con la palabra clave `it`.

```kotlin
// Función de orden superior que imprime elementos si cumplen una condición
fun imprimirSi(lista: List<Int>, fn: (Int) -> Boolean) {    
    for (elemento in lista) {
        if (fn(elemento)) {
            print("$elemento ")
        }
    }
}

// Llamada para imprimir solo los números pares
imprimirSi(lista) { it % 2 == 0 } // Imprime: 2 4.
```

Esta forma es mucho más directa que la versión larga: `imprimirSi(lista, { x: Int -> x % 2 == 0 })`. Al principio puede costar acostumbrarse, pero una vez que lo dominas, el código se vuelve mucho más ágil y expresivo.

¿Qué cosa más rara no? Si seguro que esto no lo voy a usar en la vida... Pues fíjate en, por ejemplo, la API de por ejemplo el componente `Button` de Jetpack Compose

La copio aquí *for reference*:

```kotlin
@Composable
@ComposableInferredTarget
public fun Button(
    onClick: () -> Unit,
    modifier: Modifier = Modifier,
    enabled: Boolean = true,
    shape: Shape = ButtonDefaults.shape,
    colors: ButtonColors = ButtonDefaults.buttonColors(),
    elevation: ButtonElevation? = ButtonDefaults.buttonElevation(),
    border: BorderStroke? = null,
    contentPadding: PaddingValues = ButtonDefaults.ContentPadding,
    interactionSource: MutableInteractionSource? = null,
    content: @Composable (RowScope.() -> Unit)
): Unit
```

Como ves casi todos los parámetros tienen un valor por defecto a excepción de `onClick` y `content`, que son lambdas. Esto significa que cuando creas un `Button`, **tienes que pasarle una lambda para el evento `onClick` y otra para el contenido del botón**. El lambda del contenido generalmente se usa para poner un `Text` o un `Icon` dentro del botón, y el lambda de `onClick` es lo que se ejecuta cuando el usuario pulsa el botón. Esto es un ejemplo claro de cómo las lambdas son fundamentales en la programación moderna con Kotlin y Jetpack Compose.

Por ejemplo, si quisieramos que el botón modificara un conteo cada vez que se pulsa, podríamos hacer algo así:

```kotlin
var count by remember { mutableStateOf(0) }

Button(onClick = { count++ }) {
    Text("Has pulsado $count veces")
}
```

Aquí, en este ejemplo se ve buena parte de lo que hemos aprendido. Una función de orden superior (`Button`) que recibe lambdas para manejar eventos (modificar el contador). El `content`, como es el último parámetro, se puede pasar fuera de los paréntesis (esta es la manera más habitual y por tanto la *best practice*), directamente con llaves dado que es una lambda. Ya lo hemos dicho antes, pero esta es una de esas cuestiones que conviene repetir por que son nucleares a este lenguaje y estilo de programación.

### 30. Colecciones

**Colecciones en Kotlin**: En Kotlin, el manejo de colecciones de datos como listas, mapas o conjuntos es mucho más robusto y expresivo que en Java. La mayor diferencia y ventaja es la distinción clara entre colecciones **inmutables** (solo lectura) y **mutables**. Esta separación ayuda a escribir un código más seguro y predecible.

Dominar las operaciones sobre colecciones junto con las lambdas te dará una gran cantidad de algoritmos resueltos en muy pocas líneas de código.
Para esta sección, es fundamental que comprendáis las diferentes estructuras de datos que ofrece Kotlin. 

Vamos de menos a más:

#### Arrays

Un `Array` es una colección de **tamaño fijo** que puede contener elementos del mismo tipo. En Kotlin, los arrays son objetos y se crean usando la función `arrayOf()` o `Array()`.

```kotlin
fun main() {
    val numeros: Array<Int> = arrayOf(1, 2, 3, 4, 5)
    val nombres: Array<String> = arrayOf("Ana", "Luis", "Carlos")

    // Acceder a elementos
    println(numeros[0]) // Imprime 1
    println(nombres[1]) // Imprime Luis

    // Modificar un elemento
    numeros[2] = 10
    println(numeros.joinToString()) // Imprime 1, 2, 10, 4, 5
}
```

Los arrays son estructuras de tamaño fijo y muy eficientes, especialmente cuando se trabaja con tipos primitivos o con APIs de Java. Sin embargo, en Kotlin moderno rara vez los usamos directamente: las listas inmutables son la aproximación idiomática para representar colecciones que no cambian, y ofrecen una interfaz más rica y segura. La ventaja de rendimiento de los arrays solo se nota en casos muy específicos.

#### Listas

Esto es el *bread and butter* de las colecciones en Kotlin. Una `List` es una **colección ordenada** de elementos que puede ser **inmutable** (solo lectura) o **mutable** (lectura y escritura). La inmutabilidad es la opción por defecto en Kotlin, lo que significa que una vez creada, no puedes añadir ni eliminar elementos.

```kotlin
fun main() {
    // Lista inmutable
    val listaInmutable: List<String> = listOf("Manzana", "Banana", "Cereza")
    println(listaInmutable) // Imprime [Manzana, Banana, Cereza]

    // Lista mutable
    val listaMutable: MutableList<String> = mutableListOf("Rojo", "Verde", "Azul")
    listaMutable.add("Amarillo") // Añadir un elemento
    println(listaMutable) // Imprime [Rojo, Verde, Azul, Amarillo]
}
```

> [!TIP]
> Si alguna vez en el IDE ves que el compilador se te queja al intentar llamar a, por ejemplo `add()` sobre una `List`, es porque estás usando una lista inmutable. Asegúrate de usar `MutableList` si necesitas modificar la colección. ¡Ya te digo que esto pasa con frecuencia!

Los miembros más importantes de las listas son:

- `size`: Devuelve el número de elementos en la lista.
- `lista[index]`: Accede al elemento en la posición `index`. Equivalente a `get(index)`.
- `contains(element)`: Comprueba si la lista contiene un elemento específico.
- `indexOf(element)`: Devuelve el índice **del primer elemento** que coincide con el valor dado, o -1 si no se encuentra.
- `lastIndexOf(element)`: Devuelve el índice **del último elemento** que coincide con el valor dado, o -1 si no se encuentra.
- `subList(fromIndex, toIndex)`: Devuelve una **vista** de la lista entre los índices especificados. Ojo a lo de **vista**: si modificas la sublista, también se modifica la lista original.
- `isEmpty()`: Comprueba si la lista está vacía.
- `isNotEmpty()`: Comprueba si la lista no está vacía.
- `first()`: Devuelve el primer elemento de la lista. Lanza una excepción si la lista está vacía.
- `last()`: Devuelve el último elemento de la lista. Lanza una excepción si la lista está vacía.
- `firstOrNull()`: Devuelve el primer elemento de la lista o `null` si está vacía.
- `lastOrNull()`: Devuelve el último elemento de la lista o `null` si está vacía.

Para el caso de las listas mutables debemos añadir tamibén:
- `add(element)`: Añade un elemento al final de la lista.
- `add(index, element)`: Inserta un elemento en la posición `index`.
- `remove(element)`: Elimina la primera aparición del elemento de la lista (y devuelve `true` si se eliminó). Si no se encuentra, no hace nada (aunque devuelve `false`).
- `removeAt(index)`: Elimina el elemento en la posición `index`.
- `list[index] = element`: Modifica el elemento en la posición `index`.
- `shuffle()`: Mezcla los elementos de la lista de forma aleatoria.

> [!TIP]
> A la hora de elegir colecciones, lista suele destacar si la colección es ordenada, necesitamos acceder a elementos por índice y puede contener duplicados. A más de estas condiciones se cumplan más probable es que la lista sea la mejor opción. También suele ser la opción por defecto si no tenemos un requisito específico.

Sin dedicarle un capítulo muy largo, tenemos los **Set** (en castellano decimos *conjunto*). Un `Set` es una colección que **no permite elementos duplicados** y no garantiza un orden específico (bueno esto discutible en la implementación de Kotlin, que conserva el de inserción). Al igual que las listas, pueden ser inmutables o mutables.

```kotlin
fun main() {
    // Set inmutable
    val setInmutable: Set<String> = setOf("A", "B", "C", "A") // El duplicado "A" se ignora
    println(setInmutable) // Imprime [A, B, C]

    // Set mutable
    val setMutable: MutableSet<String> = mutableSetOf("X", "Y", "Z")
    setMutable.add("W") // Añadir un elemento
    setMutable.add("X") // Intento de añadir un duplicado, no se añade
    println(setMutable) // Imprime [X, Y, Z, W]
}
```

Lo bonito de los `Set`, además de que garantizan la **unicidad** de los elementos, es que son muy eficientes para operaciones de búsqueda y eliminación, especialmente cuando se trabaja con grandes cantidades de datos. También son fantásticos para realizar operaciones de teoría de conjuntos como unión, intersección y diferencia (¡muy habituales en consultas SQL!).

En el siguiente ejemplo vamos a ver las operaciones más típicas usando conjuntos con empresas.

```kotlin
fun main() {

    val empresasColaboradoras2025 = setOf("NTT Data", "Everis", "Indra", "Accenture", "Capgemini", "Sopra Steria", "Atos", "IBM", "Oracle", "Microsoft")
    val empresasColaboradoras2026 = setOf("NTT Data", "Everis", "Capgemini", "Sopra Steria", "Atos", "IBM", "Oracle", "Microsoft", "Google", "Contoso")


    // Unión de conjuntos: Empresas que alguna vez han colaborado con nosotros
    val empresasColaboradoras = empresasColaboradoras2025.union(empresasColaboradoras2026)

    // Diferencia de conjuntos: Empresas que colaboraron en 2025 pero que dejaron de colaborar en 2026
    val empresasQueDejaronDeColaborar = empresasColaboradoras2025.subtract(empresasColaboradoras2026)

    // Intersección de conjuntos: Empresas que colaboraron en ambos años
    val empresasQueColaboraronAmbosAnos = empresasColaboradoras2025.intersect(empresasColaboradoras2026)

    println("Empresas que alguna vez han colaborado con nosotros: $empresasColaboradoras")
    println("Empresas que colaboraron en 2025 pero que dejaron de colaborar en 2026: $empresasQueDejaronDeColaborar")
    println("Empresas que colaboraron en ambos años: $empresasQueColaboraronAmbosAnos")


}
```

#### Mapas

Los mapas (`Map`) son colecciones que almacenan **pares clave-valor**. Cada clave es única y se asocia a un valor. Al igual que las listas y los conjuntos, los mapas pueden ser inmutables o mutables. En Java, el `HashMap` es la implementación más común, mientras que en Kotlin, el equivalente sería `mutableMapOf()` para mapas mutables y `mapOf()` para inmutables.

La sintaxis básica para crear un mapa es la siguiente:

```kotlin
fun main() {
    // Mapa inmutable
    val mapaInmutable: Map<String, Int> = mapOf("uno" to 1, "dos" to 2, "tres" to 3)
    println(mapaInmutable) // Imprime {uno=1, dos=2, tres=3} 

    // Mapa mutable
    val mapaMutable: MutableMap<String, Int> = mutableMapOf("A" to 10, "B" to 20)
    mapaMutable["C"] = 30 // Añadir un nuevo par clave-valor
    println(mapaMutable) // Imprime {A=10, B=20, C=30}
}
```

Donde el operador `to` crea un par clave-valor. Los mapas son ideales para situaciones donde necesitas asociar datos de manera rápida y eficiente, como almacenar configuraciones, contar ocurrencias o indexar información.

Veamos un ejemplo típico en que vamos a contar la frecuencia de palabras en un texto usando un mapa mutable. Tomaremos como referencia el primer párrafo de *El Quijote*:

```kotlin
fun main() {
    val texto = 
    """
    En un lugar de la Mancha, de cuyo nombre no quiero acordarme, no ha mucho tiempo que vivía un hidalgo de los de lanza en astillero, adarga antigua, rocín flaco y galgo corredor. Una olla de algo más vaca que carnero, salpicón las más noches, duelos y quebrantos los sábados, lantejas los viernes, algún palomino de añadidura los domingos, consumían las tres partes de su hacienda. El resto della concluían sayo de velarte, calzas de velludo para las fiestas, con sus pantuflos de lo mesmo, y los días de entresemana se honraba con su vellorí de lo más fino. Tenía en su casa una ama que pasaba de los cuarenta, y una sobrina que no llegaba a los veinte, y un mozo de campo y plaza, que así ensillaba el rocín como tomaba la podadera. Frisaba la edad de nuestro hidalgo con los cincuenta años; era de complexión recia, seco de carnes, enjuto de rostro, gran madrugador y amigo de la caza. Quieren decir que tenía el sobrenombre de Quijada, o Quesada, que en esto hay alguna diferencia en los autores que deste caso escriben; aunque por conjeturas verosímiles se deja entender que se llamaba Quijana. Pero esto importa poco a nuestro cuento: basta que en la narración dél no se salga un punto de la verdad.
    """
    .trimIndent()

    // No toméis esto como ejemplo de buenas prácticas a la hora de procesar texto, es solo un ejemplo para ilustrar el uso de mapas.

    val palabras = texto.split(Regex("[,.;:!?\\s]+"))
    val stopWords = listOf("", ",", ".", ";", ":", "!", "?", "\n")

    palabras = palabras.filterNot { it in stopWords }.map { it.lowercase() } // Filtramos signos de puntuación y espacios vacíos. Convertimos a minúsculas para que "El" y "el" se cuenten como la misma palabra.

    // println("Palabras: $palabras")

    val frecuenciaPalabras = mutableMapOf<String, Int>()

    for(palabra in palabras) {
        // Si la palabra ya está en el mapa, incrementamos su contador; si no, la añadimos con valor 1
        frecuenciaPalabras[palabra] = frecuenciaPalabras.getOrDefault(palabra, 0) + 1
    }

    // println("Frecuencia de palabras: $frecuenciaPalabras")

    // Si quisieramos ahora recorrer el mapa para mostrar cuantas veces se dice la palabra nuestro

    val palabraABuscar = "nuestro"

    for ((palabra, frecuencia) in frecuenciaPalabras) { // Típico for k, v
        if (palabra == palabraABuscar) println ("La palabra '$palabra' aparece $frecuencia veces.")    
    }

}
```

Los miembros más importantes de los mapas son:
- `size`: Devuelve el número de pares clave-valor en el mapa.
- `mapa[key]`: Accede al valor asociado a la clave `key`. Equivalente a `get(key)`.
- `getOrDefault(key, defaultValue)`: Devuelve el valor asociado a la clave `key`, o `defaultValue` si la clave no existe.
- `isEmpty()`: Comprueba si el mapa está vacío.
- `isNotEmpty()`: Comprueba si el mapa no está vacío.
- `containsKey(key)`: Comprueba si el mapa contiene una clave específica.
- `containsValue(value)`: Comprueba si el mapa contiene un valor específico.
- `keys`: Devuelve un conjunto (`Set`) de todas las claves del mapa.
- `values`: Devuelve una colección (`Collection`) de todos los valores del mapa.

Y en el caso de los mapas mutables debemos añadir:
- `put(key, value)`: Añade un par clave-valor al mapa. Si la clave ya existe, actualiza su valor.
- `remove(key)`: Elimina el par clave-valor asociado a la clave `key`. Devuelve el valor eliminado o `null` si la clave no existía.
- `mapa[key] = value`: Modifica el valor asociado a la clave `key`. Si la clave no existe, la añade al mapa.
- `clear()`: Elimina todos los pares clave-valor del mapa.
- `remove(key, value)`: Elimina el par clave-valor solo si la clave está asociada al valor especificado. Devuelve un `Boolean` indicando si se eliminó el par, ojo esto es diferente a `remove(key)`.

#### Secuencias

Sin entrar demasiado al detalle, dado que esto es un curso de iniciación, las secuencias (`Sequence`) son colecciones que permiten **procesar elementos de manera perezosa** (lazy). Esto significa que los elementos se generan y procesan bajo demanda, en lugar de cargarse todos en memoria de una vez. Esto es especialmente útil cuando trabajamos con grandes cantidades de datos o flujos infinitos. El mejor ejemplo lo encontramos en la web de Develou, y que reproduzco aquí dadas las circunstancias:

```kotlin
fun main() {
    val dragonBallparty = listOf("Vegeta", "Goku", "Piccolo", "Gohan", "Trunks").asSequence()
    val dbz = dragonBallparty
        .filter { println("1. filter($it)");it.length > 5 }
        .map { println("2. map($it)");it.take(3) }
        .sortedBy { println("3. sortedBy($it) ");it.first() }
    println(dbz.toList())
}
```

Fíjate que la salida de este programa es:

```
1. filter(Vegeta)
2. map(Vegeta)
1. filter(Goku)
1. filter(Piccolo)
2. map(Piccolo)
1. filter(Gohan)
1. filter(Trunks)
2. map(Trunks)
3. sortedBy(Pic) 
3. sortedBy(Veg) 
3. sortedBy(Tru) 
3. sortedBy(Pic) 
3. sortedBy(Tru) 
3. sortedBy(Veg) 
3. sortedBy(Tru) 
3. sortedBy(Pic) 
[Pic, Tru, Veg]
```

No se ha procesado primero todos los `filter` y luego todos los `map`, sino que se ha ido procesando cada elemento de manera perezosa, lo que demuestra la eficiencia de las secuencias. Esto es especialmente útil cuando trabajamos con grandes cantidades de datos o flujos infinitos, ya que nos permite ahorrar memoria y tiempo de procesamiento.

#### Operadores sobrecargados sobre colecciones

En Jetpack Compose es habitual que trabajemos con listas inmutables, y que creemos listas copias de la original con los elementos modificados. Esto es un patrón muy habitual en la programación funcional y en el desarrollo de interfaces de usuario reactivas. Para ello lo más habitual es utilizar los operadores `+` y `-` para añadir o eliminar elementos de una lista, respectivamente. Por ejemplo:

```kotlin
    val listaOriginal = listOf("a", "b", "c")
    val listaConElemento = listaOriginal + "d"
    val listaSinElemento = listaConElemento - "b"

    println(listaOriginal) // Imprime [a, b, c]
    println(listaConElemento) // Imprime [a, b, c, d]
    println(listaSinElemento) // Imprime [a, c, d]
```

Ahora, vamos a ver el tipico ejemplo de una función que emula el comportamiento de un `checkbox`, recibe una lista, un elemento y un booleano que indica si el elemento ha sido marcado o no. Si está marcado, lo añadimos a la lista; si no, lo eliminamos.

```kotlin
fun toggleElemento(lista: List<String>, elemento: String, isChecked: Boolean): List<String> {
    return if (isChecked) {
        lista + elemento      // lo añado
    } else {
        lista - elemento      // lo quito
    }
}

fun main() {
    var lista = listOf("Manzana")

    lista = toggleElemento(lista, "Pera", true)
    println(lista)   // [Manzana, Pera]

    lista = toggleElemento(lista, "Manzana", false)
    println(lista)   // [Pera]
}
```

### 32. Aplicando Lambdas a Colecciones: La palanca de la Programación Funcional

Veamos cómo la programación funcional simplifica tareas comunes. Imagina que queremos guardar los días de la semana en una lista e imprimirlos.

```kotlin
// Creamos una lista inmutable
val diasSemana: List<String> = listOf("lunes", "martes", "miércoles", "jueves", "viernes", "sábado", "domingo")
```

**La forma "tradicional" (imperativa) con un `for`:**

```kotlin
// Imprimir todos los días
for (dia in diasSemana) {
    println(dia)
}
```

**La forma funcional y concisa de Kotlin:**

```kotlin
// Usamos la función de orden superior forEach con una lambda
diasSemana.forEach { println(it) }

// Equivalente con una referencia a función (sección 27)
diasSemana.forEach(::println)
```

Ahora, si quisiéramos mostrar solo los días que empiezan por "m":

**Forma imperativa:**

```kotlin
for (dia in diasSemana) {
    if (dia.startsWith("m")) {
        println(dia)
    }
}
```

**Forma funcional:**

```kotlin
// Encadenamos dos operaciones: filtrar y luego imprimir cada resultado
diasSemana.filter { it.startsWith("m") }.forEach { println(it) }
```

Como puedes ver, el enfoque funcional es más directo y describe "qué" queremos hacer, en lugar de "cómo" hacerlo paso a paso. Incluso los rangos, al ser iterables, se benefician de estos métodos.

```kotlin
// Imprimir los números divisibles por 5 del 1 al 40
(1..40).filter { it % 5 == 0 }.forEach { println(it) }
```

Las más importantes funciones de orden superior para colecciones son:
- `forEach`: Itera sobre cada elemento de la colección y ejecuta una acción.
- `filter`: Devuelve una nueva colección con los elementos que cumplen una condición.
- `map`: Transforma cada elemento de la colección y devuelve una nueva colección con los resultados.
- `reduce`: Combina todos los elementos de la colección en un solo valor, aplicando una operación acumulativa.
- `find`: Busca el primer elemento que cumple una condición y lo devuelve, o `null` si no se encuentra.
- `any`: Devuelve `true` si al menos un elemento cumple una condición.
- `all`: Devuelve `true` si todos los elementos cumplen una condición.
- `none`: Devuelve `true` si ningún elemento cumple una condición.
- `groupBy`: Agrupa los elementos de la colección según una clave y devuelve un mapa.
- `sortedBy`: Devuelve una nueva colección ordenada según un criterio.

Otras funciones de orden superior muy útiles aunque no específicas de colecciones son:
- `let`: Ejecuta un bloque de código con el objeto como argumento y devuelve el resultado
- `run`: Similar a `let`, pero se ejecuta en el contexto del objeto y devuelve el resultado del bloque.
- `apply`: Ejecuta un bloque de código en el contexto del objeto y devuelve el objeto.
- `also`: Similar a `apply`, pero se ejecuta con el objeto como argumento y devuelve el objeto.

No te agobies, ya las irás encontrando progresivamente en el código y en la documentación de Kotlin. La idea es que te familiarices con ellas y las uses cuando tengan sentido. Ahora `forEach`, `filter` y `map` son las más habituales y las que más se usan en Kotlin, especialmente en Jetpack Compose.


> [!NOTE]
> En Android encontraremos otra función de orden superior muy útil que es `update`, que se usa para actualizar el estado de un `MutableStateFlow` de manera segura y atómica. Esto es especialmente importante en entornos multihilo, donde varias partes del código pueden intentar modificar el mismo estado al mismo tiempo. La función `update` garantiza que la actualización se realice de manera consistente y evita condiciones de carrera.

### 34. Programación Orientada a Objetos (POO) en Kotlin

Llegamos al último bloque del tema, y aquí jugáis con ventaja: la POO ya la conocéis de Java. Clases, objetos, atributos, métodos, herencia, polimorfismo... los conceptos son exactamente los mismos. Lo que cambia es la **cantidad de ceremonia** que hay que escribir para expresarlos.

Kotlin parte de una observación bastante incómoda para Java: en una clase de datos, la mayor parte del código no lo escribe una persona, lo genera el IDE. Getters, setters, `equals()`, `hashCode()`, `toString()`, constructores... Si el IDE puede generarlo, ¿por qué no lo genera directamente el compilador y nos ahorramos la molestia? Esa es, resumida en una frase, toda la filosofía de la POO en Kotlin.

Vamos a verlo con el foco puesto donde nos interesa: cada apartado termina con el sitio concreto en el que eso aparece en Android o en Jetpack Compose.

#### Clases y constructor primario

En Java, declarar una clase con dos atributos y su constructor son unas quince líneas. En Kotlin, la clase y su constructor se declaran **en la misma línea**:

```kotlin
class Persona(val nombre: String, var edad: Int)
```

Eso es una clase completa. No necesita llaves si no tiene cuerpo. Lo que va entre paréntesis después del nombre de la clase se llama **constructor primario**, y no es solo una lista de parámetros: al marcarlos con `val` o `var` estamos declarando **propiedades** de la clase al mismo tiempo.

Para crear objetos, **en Kotlin no existe `new`**:

```kotlin
fun main() {
    val ana = Persona("Ana", 30)
    println(ana.nombre)   // Ana
    ana.edad = 31         // Funciona porque edad es var
    // ana.nombre = "Eva" // ERROR de compilación: nombre es val
}
```

Fijaos en el detalle: `val`/`var` en el constructor no controla solo la mutabilidad de una variable local, sino que decide **si esa propiedad del objeto tendrá setter o no**. Es la misma distinción de la [sección 5](#5-mutabilidad-val-vs-var), aplicada a los objetos.

Y como el constructor primario es, a efectos prácticos, una función, hereda todo lo que vimos en la [sección 22](#22-funciones): **valores por defecto** y **argumentos con nombre**.

```kotlin
class Persona(
    val nombre: String,
    var edad: Int = 0,
    val email: String? = null
)

val ana = Persona("Ana", 30, "ana@ejemplo.com")
val bea = Persona("Bea")                       // edad = 0, email = null
val carlos = Persona(nombre = "Carlos", email = "c@ejemplo.com")  // se salta edad
```

> [!NOTE]
> Esto explica algo que ya visteis sin entenderlo del todo en la [sección 27](#27-lambdas-en-kotlin). Cuando miramos la firma del `Button` de Compose, casi todos los parámetros tenían un valor por defecto (`modifier: Modifier = Modifier`, `enabled: Boolean = true`...). Ese es exactamente el mecanismo que acabamos de ver. Por eso en Kotlin apenas se usan las sobrecargas de constructor que en Java eran obligatorias: un constructor con valores por defecto sustituye a cinco constructores sobrecargados.

#### Propiedades, no atributos

Este es el cambio conceptual más importante del apartado, y el que más confunde viniendo de Java.

En Java tenéis **campos** (privados) y **métodos de acceso** (`getNombre()`, `setNombre()`). En Kotlin tenéis **propiedades**: un único concepto que engloba el campo y sus accesores. Cuando escribís `persona.nombre`, no estáis accediendo al campo directamente: estáis llamando al getter, que Kotlin ha generado por vosotros.

```kotlin
class Persona(val nombre: String, var edad: Int)

// Kotlin genera por debajo: getNombre(), getEdad(), setEdad()
// Pero tú escribes:
persona.edad = 31       // llama al setter
println(persona.edad)   // llama al getter
```

Las propiedades también pueden declararse en el **cuerpo** de la clase, no solo en el constructor:

```kotlin
class Persona(val nombre: String, var edad: Int) {
    var apodo: String = ""              // propiedad con valor inicial
    val creadoEn: Long = System.currentTimeMillis()
}
```

##### Propiedades calculadas (getter personalizado)

Aquí está la parte que de verdad merece la pena. Una propiedad puede **no almacenar nada** y calcular su valor cada vez que se consulta. Basta con darle un `get()` propio:

```kotlin
class Persona(val nombre: String, val apellido: String, var edad: Int) {

    val nombreCompleto: String
        get() = "$nombre $apellido"

    val mayorDeEdad: Boolean
        get() = edad >= 18
}

fun main() {
    val ana = Persona("Ana", "García", 17)
    println(ana.nombreCompleto)  // Ana García
    println(ana.mayorDeEdad)     // false
    ana.edad = 18
    println(ana.mayorDeEdad)     // true  ← se recalcula solo
}
```

Esto en Java sería un método `esMayorDeEdad()`. En Kotlin lo escribimos como una propiedad porque **conceptualmente es un dato del objeto, no una acción que el objeto realiza**. La regla de estilo es esa: si responde a "¿qué eres?" es una propiedad; si responde a "¿qué haces?" es una función.

> [!NOTE]
> Fijaos en que `mayorDeEdad` **tiene que ser `val`** y no puede tener valor inicial: no guarda nada, se deriva de `edad`. Si lo hubiéramos escrito como `val mayorDeEdad = edad >= 18`, se calcularía **una sola vez al construir el objeto** y se quedaría congelado para siempre. Es un error clásico y además silencioso, porque compila perfectamente.

También existe el setter personalizado, donde `field` es el nombre reservado para referirse al valor almacenado (el *backing field*). Se usa mucho menos, pero conviene reconocerlo:

```kotlin
class Producto {
    var precio: Double = 0.0
        set(valor) {
            field = if (valor < 0) 0.0 else valor   // nunca guardamos negativos
        }
}
```

> [!WARNING]
> Dentro del setter **nunca** escribáis `precio = valor`: eso vuelve a llamar al setter y os montáis una recursión infinita hasta el `StackOverflowError`. Para eso está `field`.

**En Android:** las propiedades calculadas son el pan de cada día en los `ViewModel` y en las clases de estado. Y en la práctica de esta unidad, el valor de una carta del siete y medio (del 1 al 7 vale su número, las figuras valen 0,5) es exactamente esto: una propiedad calculada.

#### El bloque `init` y los constructores secundarios

Si el constructor primario solo puede asignar propiedades, ¿dónde ponemos la lógica de inicialización? En un bloque `init`:

```kotlin
class Alumno(val nombre: String, val nota: Int) {

    val aprobado: Boolean

    init {
        require(nota in 0..10) { "La nota debe estar entre 0 y 10, recibida: $nota" }
        aprobado = nota >= 5
        println("Alumno $nombre creado")
    }
}
```

`require()` es una función de la librería estándar que lanza `IllegalArgumentException` si la condición no se cumple. Es la forma idiomática de validar parámetros en Kotlin, y usa un rango como los de la [sección 17](#17-rangos).

Kotlin también admite **constructores secundarios** con la palabra `constructor`, que deben delegar en el primario con `this(...)`:

```kotlin
class Persona(val nombre: String, var edad: Int) {
    constructor(nombre: String) : this(nombre, 0)
}
```

Pero honestamente: **esto casi nunca hace falta**. El ejemplo de arriba se resuelve mejor con `var edad: Int = 0` en el constructor primario. Os lo enseño para que lo reconozcáis al leer código ajeno (sobre todo código traducido desde Java), no para que lo uséis.

#### Herencia: en Kotlin todo está cerrado por defecto

Primera diferencia gorda con Java: **en Kotlin las clases son `final` por defecto**. No se puede heredar de una clase salvo que quien la escribió lo permita explícitamente con `open`. Lo mismo vale para los métodos.

```kotlin
open class Animal(val nombre: String) {          // open: se puede heredar
    open fun hacerSonido() = println("...")      // open: se puede sobrescribir
    fun dormir() = println("$nombre duerme")     // final: NO se puede sobrescribir
}

class Perro(nombre: String) : Animal(nombre) {
    override fun hacerSonido() = println("$nombre dice: ¡Guau!")
}

class Gato(nombre: String) : Animal(nombre) {
    override fun hacerSonido() = println("$nombre dice: ¡Miau!")
}
```

Tres detalles de sintaxis que cambian respecto a Java:

| Java | Kotlin |
| ---- | ---- |
| `extends` / `implements` | Los dos son `:` |
| `@Override` (anotación opcional) | `override` (palabra clave **obligatoria**) |
| `super(nombre)` dentro del constructor | `: Animal(nombre)` en la cabecera de la clase |

Fijaos en que en `class Perro(nombre: String)` el parámetro **no** lleva `val`: no estamos declarando una propiedad nueva, solo recogiendo un valor para pasárselo al constructor de `Animal`, que es quien tiene la propiedad `nombre`. Si le pusierais `val`, tendríais dos propiedades llamadas igual y el compilador se quejaría.

El polimorfismo funciona igual que en Java:

```kotlin
val animales: List<Animal> = listOf(Perro("Toby"), Gato("Misi"))
animales.forEach { it.hacerSonido() }
// Toby dice: ¡Guau!
// Misi dice: ¡Miau!
```

Y `super` sigue sirviendo para llamar a la implementación del padre:

```kotlin
class Cachorro(nombre: String) : Animal(nombre) {
    override fun hacerSonido() {
        super.hacerSonido()
        println("(pero más flojito)")
    }
}
```

> [!NOTE]
> ¿Por qué cerrado por defecto? Porque heredar de una clase que no fue diseñada para ser heredada rompe cosas. Es el famoso consejo de *Effective Java* («diseña y documenta para la herencia, o prohíbela»), que Java dejó como recomendación y Kotlin convirtió en el comportamiento por defecto. En la práctica, en Android vais a **usar** herencia mucho más de lo que vais a **diseñarla**.

Las clases abstractas y las interfaces existen y se comportan como esperáis. Las abstractas son `open` automáticamente, así que no hace falta marcarlas:

```kotlin
abstract class Figura {
    abstract val area: Double              // sin implementación
    fun describir() = "Área: $area"        // con implementación
}

interface Dibujable {
    fun dibujar()
    fun borrar() = println("Borrando...")  // las interfaces admiten implementación por defecto
}

class Circulo(val radio: Double) : Figura(), Dibujable {
    override val area: Double
        get() = Math.PI * radio * radio

    override fun dibujar() = println("Dibujando círculo de radio $radio")
}
```

Notad que la clase lleva paréntesis (`Figura()`, porque se construye) y la interfaz no (`Dibujable`, porque no se construye). Ese es el truco para distinguirlas de un vistazo cuando leáis una cabecera de clase.

**En Android** esto lo vais a ver el primer día, aunque no lo escribáis vosotros:

```kotlin
class MainActivity : ComponentActivity() {          // heredamos de una clase del framework
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)          // obligatorio llamar al padre
        // ...
    }
}

class ContadorViewModel : ViewModel() { /* ... */ }
```

#### `data class`: la estrella del lenguaje

Llegamos a lo que de verdad justifica este apartado. Una `data class` es una clase cuyo propósito es **contener datos**, y para la que el compilador genera automáticamente todo lo que en Java teníais que generar con el IDE:

```kotlin
data class Persona(val nombre: String, val edad: Int)
```

Con esa línea, el compilador os regala:

| Qué genera | Para qué sirve |
| ---- | ---- |
| `equals()` / `hashCode()` | Comparar por **contenido** en lugar de por referencia |
| `toString()` | Imprimir el objeto de forma legible |
| `copy()` | Crear una copia cambiando solo lo que queramos |
| `component1()`, `component2()`... | Desestructurar (lo vemos en el apartado siguiente) |

Y la diferencia se nota inmediatamente:

```kotlin
class PersonaNormal(val nombre: String, val edad: Int)
data class PersonaData(val nombre: String, val edad: Int)

fun main() {
    val a1 = PersonaNormal("Ana", 30)
    val a2 = PersonaNormal("Ana", 30)
    println(a1 == a2)   // false  ← compara referencias
    println(a1)         // PersonaNormal@6d06d69c

    val b1 = PersonaData("Ana", 30)
    val b2 = PersonaData("Ana", 30)
    println(b1 == b2)   // true   ← compara contenido
    println(b1)         // PersonaData(nombre=Ana, edad=30)
}
```

Ese `toString()` gratis, por cierto, os resuelve media práctica: imprimir una lista de objetos deja de ser una ristra de `@6d06d69c`.

##### El patrón `.copy()`

Esta es la función que más vais a usar en Android, así que merece su propio apartado.

La idea es que, si las propiedades son `val` (inmutables), no podemos modificar un objeto... pero sí podemos crear uno nuevo igual salvo por lo que nos interese cambiar:

```kotlin
data class Persona(val nombre: String, val edad: Int, val email: String? = null)

val ana = Persona("Ana", 30, "ana@ejemplo.com")

val anaCumpleAnios = ana.copy(edad = 31)
// Persona(nombre=Ana, edad=31, email=ana@ejemplo.com)

println(ana)  // Persona(nombre=Ana, edad=30, ...)  ← el original NO se ha tocado
```

`copy()` toma todos los valores del objeto original y solo sustituye los que le indiquéis **por nombre**. Es, literalmente, "dame otro igual pero con esto cambiado".

> [!TIP]
> Usad **siempre argumentos con nombre** en `copy()`. Si escribís `ana.copy(31)` funciona, pero estáis sustituyendo el *primer* parámetro (`nombre`) por un `31`, lo cual ni siquiera compila aquí, pero sí compilaría si los dos primeros campos fueran del mismo tipo. `copy(edad = 31)` dice exactamente lo que hace y no se rompe si mañana reordenáis el constructor.

**Por qué esto es tan importante en Android.** En Jetpack Compose, la interfaz se redibuja (*recomposición*) cuando cambia el estado. Para que Compose detecte ese cambio, necesita comparar el estado nuevo con el viejo, y para eso usa `equals()`. Si mutáis un objeto por dentro (`estado.cargando = false`), la referencia es la misma, `equals()` da `true` y **Compose no se entera de que algo cambió**: la pantalla se queda congelada. Si en cambio creáis un objeto nuevo con `copy()`, la comparación detecta la diferencia y la UI se actualiza.

De ahí sale el patrón que veréis en absolutamente todos los `ViewModel`:

```kotlin
data class PantallaUiState(
    val cargando: Boolean = false,
    val alumnos: List<String> = emptyList(),
    val error: String? = null
)

class AlumnosViewModel : ViewModel() {
    private val _uiState = MutableStateFlow(PantallaUiState())
    val uiState: StateFlow<PantallaUiState> = _uiState.asStateFlow()

    fun cargar() {
        _uiState.update { it.copy(cargando = true, error = null) }
        // ... obtenemos los datos ...
        _uiState.update { it.copy(cargando = false, alumnos = listOf("Ana", "Bea")) }
    }
}
```

No hace falta que entendáis todavía `MutableStateFlow` ni `update` (eso es materia de temas posteriores). Quedaos con la forma: **un `data class` con todas las propiedades `val`, y cada cambio de estado expresado como un `copy()`**. Ese es el idioma de una app Android moderna, y por eso esta sección, que parece teoría de POO clásica, es en realidad la base de todo lo que viene después.

> [!WARNING]
> Dos trampas de las `data class`:
>
> 1. `equals()`, `hashCode()`, `toString()` y `copy()` **solo tienen en cuenta las propiedades del constructor primario**. Si declaráis una propiedad en el cuerpo de la clase, queda fuera de todas ellas:
>
>    ```kotlin
>    data class Usuario(val id: Int) {
>        var apodo: String = ""    // ← ignorada por equals, toString y copy
>    }
>
>    val u1 = Usuario(1)
>    val u2 = Usuario(1)
>    u1.apodo = "Ana"
>
>    println(u1 == u2)   // true, aunque los apodos sean distintos
>    println(u1)         // Usuario(id=1)  ← el apodo ni siquiera aparece
>    ```
>
> 2. `copy()` hace una **copia superficial**. Si una propiedad es una lista mutable, la copia y el original comparten la misma lista. Por eso la recomendación es `val` y colecciones de solo lectura (`List`, no `MutableList`), tal y como vimos en la [sección 30](#30-colecciones).

Requisitos para que una clase pueda ser `data class`: debe tener **al menos un parámetro** en el constructor primario, y todos ellos deben ser `val` o `var`. No pueden ser `abstract`, `open` ni `sealed`.

##### ¿Cuándo `class` y cuándo `data class`?

| Usa `data class` | Usa `class` normal |
| ---- | ---- |
| El objeto **es** un conjunto de datos | El objeto **hace** cosas |
| Quieres compararlo por contenido | La identidad importa (dos objetos distintos son distintos) |
| Estado de UI, modelos, respuestas de una API | ViewModels, repositorios, servicios, controladores |

Regla rápida: si al leer la clase pensáis "esto en Java sería un POJO con puros getters", es una `data class`.

#### Desestructuración

Una `data class` genera, además, funciones `component1()`, `component2()`, etc., una por cada propiedad del constructor primario. Eso permite **desmontar un objeto en varias variables de golpe**:

```kotlin
data class Persona(val nombre: String, val edad: Int)

val ana = Persona("Ana", 30)

val (nombre, edad) = ana        // desestructuración
println("$nombre tiene $edad años")   // Ana tiene 30 años
```

Esa línea equivale exactamente a:

```kotlin
val nombre = ana.component1()
val edad = ana.component2()
```

Podéis ignorar componentes que no os interesen con el guion bajo `_`, igual que hacíamos con los parámetros de las lambdas:

```kotlin
val (_, edad) = ana    // solo queremos la edad
```

Donde esto se vuelve realmente cómodo es recorriendo mapas y listas de pares, enlazando con lo que visteis en la [sección 30](#30-colecciones):

```kotlin
val notas = mapOf("Ana" to 9, "Bea" to 7, "Carlos" to 5)

for ((alumno, nota) in notas) {
    println("$alumno ha sacado un $nota")
}
```

Ese `(alumno, nota)` funciona porque cada entrada del mapa es desestructurable. Lo mismo dentro de una lambda:

```kotlin
val personas = listOf(Persona("Ana", 30), Persona("Bea", 25))

personas.forEach { (nombre, edad) ->
    println("$nombre → $edad")
}

// Y combinado con lo de la sección 32
val mayores = personas.filter { (_, edad) -> edad >= 28 }
```

> [!WARNING]
> **La desestructuración es posicional, no por nombre.** `val (nombre, edad) = ana` no busca las propiedades llamadas `nombre` y `edad`: coge la primera y la segunda **en el orden del constructor**. Si mañana alguien reordena el constructor de `Persona`, este código **sigue compilando** pero asigna los valores cambiados. Es de los pocos sitios de Kotlin donde el compilador no os cubre las espaldas, así que usadla con objetos pequeños y estables (pares, entradas de mapa) y no con `data class` de diez campos.

#### `enum class`: conjuntos cerrados de valores

Cuando una propiedad solo puede tomar un número limitado y conocido de valores, la herramienta correcta **no** es un `String` ni un `Int`, es un `enum class`:

```kotlin
enum class Palo {
    OROS, COPAS, ESPADAS, BASTOS
}

val palo = Palo.COPAS
println(palo)         // COPAS
println(palo.name)    // COPAS  (el nombre como String)
println(palo.ordinal) // 1      (su posición, empezando en 0)
```

La ventaja frente a un `String` es que **el compilador conoce todos los valores posibles**. No podéis escribir `Palo.CORAZONES` por error: no compila. Con `String` habríais descubierto la errata en tiempo de ejecución, con suerte.

Los enums de Kotlin pueden llevar constructor y propiedades, igual que los de Java:

```kotlin
enum class Palo(val simbolo: String) {
    OROS("🪙"),
    COPAS("🍷"),
    ESPADAS("⚔️"),
    BASTOS("🪵");              // ← ojo al punto y coma

    fun descripcion() = "$simbolo ${name.lowercase()}"
}

println(Palo.OROS.descripcion())   // 🪙 oros
```

Ese punto y coma tras el último valor es obligatorio si después hay propiedades o funciones. Es de las poquísimas veces que Kotlin os pide un `;`.

Para recorrer todos los valores se usa `entries`:

```kotlin
for (palo in Palo.entries) {
    println(palo.descripcion())
}

val paloAleatorio = Palo.entries.random()
```

> [!NOTE]
> Históricamente se usaba `Palo.values()`, que sigue funcionando pero está desaconsejada desde Kotlin 1.9. `values()` crea un array nuevo **cada vez que se llama**, mientras que `entries` devuelve una `List` ya construida. Si veis `values()` en tutoriales antiguos, ya sabéis por qué.

Y la combinación que de verdad importa, enlazando con la [sección 19](#19-sentencia-when): cuando hacéis un `when` sobre un enum y cubrís todos los casos, **el `else` deja de ser necesario**:

```kotlin
fun color(palo: Palo): String = when (palo) {
    Palo.OROS -> "Amarillo"
    Palo.COPAS -> "Rojo"
    Palo.ESPADAS -> "Azul"
    Palo.BASTOS -> "Verde"
}   // sin else: el compilador sabe que no hay más palos
```

Esto es mucho más que una comodidad estética. Si mañana añadís un quinto palo al enum, **este `when` deja de compilar** y el compilador os lleva de la mano hasta todos los sitios que hay que actualizar. Con un `else` genérico, en cambio, el código habría seguido compilando y fallando en silencio. Es exactamente el tipo de error que un lenguaje bien diseñado debería impedir.

**En la práctica de esta unidad** vais a necesitar justo esto: un `enum class Palo` con los cuatro palos de la baraja y, si queréis, un símbolo asociado para pintarlos por terminal.

#### `sealed class`: enums con datos

Os prometí en la [sección 19](#19-sentencia-when) que hablaríamos de las *sealed classes*, y este es el momento, aunque sea de pasada, porque en Android son omnipresentes.

Un `enum` es un conjunto cerrado de **valores**. Una `sealed class` (o `sealed interface`) es un conjunto cerrado de **tipos**, donde cada uno puede llevar datos distintos:

```kotlin
sealed interface ResultadoUi {
    object Cargando : ResultadoUi
    data class Exito(val alumnos: List<String>) : ResultadoUi
    data class Error(val mensaje: String) : ResultadoUi
}
```

"Sellada" significa que **solo puede haber esas tres implementaciones**, y el compilador lo sabe. Así que el `when` vuelve a ser exhaustivo sin `else`, pero además, dentro de cada rama, Kotlin ya conoce el tipo concreto y podéis acceder a sus datos sin ningún casteo:

```kotlin
fun pintar(resultado: ResultadoUi) = when (resultado) {
    is ResultadoUi.Cargando -> println("Cargando...")
    is ResultadoUi.Exito -> println("${resultado.alumnos.size} alumnos")   // sabe que hay .alumnos
    is ResultadoUi.Error -> println("Error: ${resultado.mensaje}")         // sabe que hay .mensaje
}
```

Compárenlo con la alternativa de tener un único `data class` con `cargando`, `datos` y `error` a la vez: ahí son posibles estados absurdos (cargando **y** con error **y** con datos). Con una `sealed`, esos estados sencillamente no se pueden construir.

No hace falta que lo dominéis ahora. Quedaos con el concepto y con el nombre, porque cuando lleguemos a modelar el estado de una pantalla en Compose será la primera herramienta que saquemos.

#### Funciones de extensión

Y cerramos con la que probablemente sea la característica más sorprendente de Kotlin: **podéis añadir funciones a clases que no habéis escrito y cuyo código fuente no tenéis**. Sin heredar, sin decoradores, sin envoltorios.

```kotlin
fun String.esPalindromo(): Boolean {
    val limpio = this.lowercase().replace(" ", "")
    return limpio == limpio.reversed()
}

fun main() {
    println("Anita lava la tina".esPalindromo())   // true
    println("Hola mundo".esPalindromo())           // false
}
```

La sintaxis es: `fun TipoQueExtiendo.nombreFuncion()`. Dentro, `this` es el objeto sobre el que se llama (el **receptor**), y se puede omitir igual que en cualquier método.

También existen las **propiedades de extensión**, que siguen la misma lógica:

```kotlin
val String.iniciales: String
    get() = this.split(" ").map { it.first() }.joinToString("")

println("Ada Lovelace King".iniciales)   // ALK
```

¿Cómo funciona esto por debajo? No hay magia ni se modifica la clase `String`: Kotlin compila la extensión a una **función estática normal** que recibe el receptor como primer parámetro. Lo que hace el compilador es dejaros escribirla con notación de punto. De ahí salen sus dos limitaciones:

> [!WARNING]
> 1. **No tienen acceso a los miembros privados** de la clase que extienden. Solo ven lo que vería cualquiera desde fuera.
> 2. **Se resuelven estáticamente**, así que no son polimórficas y **no pueden sobrescribir un método existente**. Si la clase ya tiene un método con esa firma, gana siempre el método de la clase y vuestra extensión no se llamará nunca (el IDE os avisará con un warning).

**En Android esto está por todas partes.** De hecho ya lo habéis usado sin saberlo: en Compose, `Modifier.padding(16.dp)`, `Modifier.fillMaxWidth()` y prácticamente todo lo que encadenáis a un `Modifier` **son funciones de extensión**. La firma real es `fun Modifier.padding(all: Dp): Modifier`. Por eso se pueden encadenar indefinidamente: cada una recibe un `Modifier` y devuelve otro.

Y el caso clásico para ahorrar código repetitivo en una app:

```kotlin
fun Context.toast(mensaje: String) {
    Toast.makeText(this, mensaje, Toast.LENGTH_SHORT).show()
}

// A partir de ahora, desde cualquier Activity:
toast("Guardado correctamente")
```

> [!TIP]
> El criterio para decidir si algo debe ser una extensión: usadlas cuando la función **tiene sentido conceptualmente como parte de esa clase** pero no podéis (o no debéis) modificarla. No las uséis como cajón de sastre para meter utilidades sueltas: una extensión de `String` que solo tiene sentido en vuestro dominio concreto contamina el autocompletado de todos los `String` del proyecto.

#### Recapitulando

| Herramienta | Cuándo usarla | Dónde aparece en Android |
| ---- | ---- | ---- |
| `class` | El objeto hace cosas | ViewModels, repositorios |
| `data class` | El objeto contiene datos | Estados de UI, modelos, respuestas de API |
| `.copy()` | Cambiar un dato sin mutar el original | Cada actualización de estado en Compose |
| Propiedad calculada | Un dato que se deriva de otros | Estados derivados, formateo |
| `enum class` | Conjunto cerrado de valores | Pestañas, filtros, tipos fijos |
| `sealed class` | Conjunto cerrado de tipos con datos | Estado de pantalla (cargando/éxito/error) |
| Extensión | Añadir capacidades a una clase ajena | `Modifier`, utilidades sobre `Context` |

Con esto tenéis ya todas las piezas del lenguaje que necesitáis para la práctica de la unidad: la baraja usará un `enum class` para los palos, una `data class Carta` con una propiedad calculada para su valor, y las funciones de colecciones de la [sección 32](#32-aplicando-lambdas-a-colecciones-la-palanca-de-la-programación-funcional) para generarla y barajarla.

### Práctica de la unidad:  Siete y medio en Kotlin

Vamos a desarrollar una versión sencilla del juego de cartas **Siete y medio** que funcionará completamente por terminal.

El objetivo de la práctica es aplicar los conceptos básicos de Kotlin vistos hasta ahora: variables, funciones, estructuras de control, colecciones, clases, `data class`, enumeraciones y propiedades calculadas.

## Reglas del juego

Se utilizará una **baraja española** formada por los siguientes palos:

* Oros
* Copas
* Espadas
* Bastos

Cada palo contiene las cartas:

`1, 2, 3, 4, 5, 6, 7, 10, 11 y 12`

Las cartas del **1 al 7** valen tantos puntos como indica su número.

Las figuras (`10`, `11` y `12`) valen **0,5 puntos**.

El objetivo es conseguir una puntuación lo más cercana posible a **7,5 puntos sin superarla**.

Si un jugador supera los **7,5 puntos**, pierde automáticamente la ronda.

## Funcionamiento del programa

Al iniciar el programa deberá aparecer un menú principal similar al siguiente:

```text
=== SIETE Y MEDIO ===

1. Nueva partida
2. Salir
```

Si se selecciona **Nueva partida**, se crea y baraja una nueva baraja y comienza la ronda.

Cada jugador juega su turno de forma independiente.

Al comenzar su turno recibe una carta:

```text
Turno del jugador 1

Has recibido:
5 de Oros
```

El programa **no mostrará la puntuación acumulada del jugador**. Será el propio jugador quien deberá llevar mentalmente la cuenta de sus puntos.

Después de recibir cada carta podrá elegir entre:

```text
1. Pedir carta
2. Plantarse
```

Si pide una nueva carta, esta se mostrará por pantalla y se volverá a ofrecer la misma decisión.

Por ejemplo:

```text
Has recibido:
12 de Espadas

1. Pedir carta
2. Plantarse
```

Si al recibir una carta el jugador supera los **7,5 puntos**, el programa deberá detectarlo automáticamente:

```text
Has recibido:
6 de Bastos

¡Te has pasado!
```

En ese momento termina inmediatamente su turno y ya no puede pedir más cartas.

Si decide **plantarse**, conserva la puntuación obtenida y comienza el turno del siguiente jugador.

## Final de la partida

Cuando todos los jugadores hayan terminado su turno, el programa comparará sus puntuaciones.

Un jugador que haya superado los **7,5 puntos** queda eliminado.

Entre los jugadores que no se hayan pasado, gana aquel cuya puntuación esté más cerca de 7,5, es decir, aquel que tenga la puntuación más alta.

Ejemplo:

```text
=== RESULTADO ===

Jugador 1: 7 puntos
Jugador 2: 6,5 puntos

¡Gana el jugador 1!
```

Si ambos jugadores obtienen exactamente la misma puntuación:

```text
¡Empate!
```

Si ambos jugadores se han pasado:

```text
Los dos jugadores se han pasado.
No hay ganador.
```

Una vez mostrado el resultado, el programa volverá al **menú principal**, desde donde se podrá comenzar una nueva partida o salir.

# Algunas pistas para diseñar el programa

No existe una única solución correcta, pero puedes apoyarte en las siguientes ideas.

### Representar los palos

Crea un `enum class` que represente los cuatro palos posibles de la baraja.

```text
Palo
 ├── OROS
 ├── COPAS
 ├── ESPADAS
 └── BASTOS
```

Puedes hacer que cada palo tenga además algún dato asociado que permita representarlo de forma más visual por terminal.

### Representar una carta

Crea una `data class Carta`.

Una carta deberá almacenar, como mínimo:

* su número;
* su palo.

Además, puede tener una **propiedad calculada** que indique cuánto vale esa carta en el juego.

Recuerda:

* del 1 al 7 → valor normal;
* 10, 11 y 12 → 0,5 puntos.

También puedes crear un método que devuelva una representación de la carta adecuada para mostrarla por terminal.

### Crear la baraja

La baraja deberá contener todas las combinaciones posibles de números y palos.

Piensa cómo podrías generarla utilizando:

* una colección con los números válidos;
* todos los valores disponibles en `Palo`;
* uno o varios bucles.

Antes de empezar una partida deberás **barajar las cartas**.

### Robar una carta

Cuando un jugador pida una carta, esta deberá obtenerse de la baraja.

Una carta que ya ha sido repartida **no puede volver a aparecer durante esa partida**.

### Controlar el turno

Durante el turno de un jugador tendrás que repetir varias veces el mismo proceso:

1. mostrar la carta recibida;
2. comprobar si se ha pasado;
3. si no se ha pasado, preguntarle si quiere otra carta;
4. continuar hasta que se plante o supere los 7,5 puntos.

Piensa qué estructura de control es especialmente adecuada para repetir este proceso.

### Organizar el programa

Evita escribir todo el juego dentro de `main()`.

Intenta dividir el programa en funciones con responsabilidades concretas. Por ejemplo, podrías necesitar funciones relacionadas con:

* crear una baraja;
* robar una carta;
* jugar el turno de un jugador;
* calcular una puntuación;
* decidir el ganador;
* mostrar el menú principal.

Los nombres y la organización exacta forman parte del ejercicio.

## Objetivo

El programa deberá permitir jugar sucesivas partidas completas de **Siete y medio** hasta que el usuario seleccione la opción de salir.

No es necesario utilizar interfaz gráfica ni Android: toda la interacción se realizará mediante **entrada y salida estándar por terminal**.
