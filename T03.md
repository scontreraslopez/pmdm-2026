## Descarga e instalación

No hay complicaciones para la instalación. Sí que es necesario tener una máquina relativamente potente, pues la emulación de un dispositivo Android no es baladí. Se recomienda tener al menos 8Gb de RAM y un disco SSD.

Las versiones más recientes de Android Studio ya incluyen un JDK (Java Development Kit). Si por alguna razón no lo detecta, el propio instalador te guiará para descargar e instalar una versión compatible, por lo que no es necesaria una instalación previa.

> [!TIP]
> La forma más cómoda de instalar y, sobre todo, de **mantener actualizado** Android Studio es la [JetBrains Toolbox App](https://www.jetbrains.com/toolbox-app/). Desde ella instalas Android Studio con un clic y te avisa de cada nueva versión para actualizar sin tener que descargar y reinstalar a mano. Además, te permite convivir con varias versiones (por ejemplo, la estable y una *preview*) y gestionar desde el mismo sitio el resto de IDEs de JetBrains, como IntelliJ IDEA.

Una cosa interesante es que en Android Studio podemos activar el *soft-wrap*, es decir, que las líneas largas se ajusten al ancho de la ventana. Pulsa `Control + Shift + A`, escribe *soft-wrap* y tendrás el *toggle* `Active Editor: Soft-Wrap` para activarlo o desactivarlo.

## ¿Por qué Jetpack Compose?

Antes de crear nuestra primera app conviene entender por qué el código que vamos a ver tiene la pinta que tiene. Android lleva desde 2008 con un sistema para construir interfaces, el **sistema de Views**, y en 2021 Google lanzó uno nuevo, **Jetpack Compose**, que es el que usaremos en todo el curso.

### El sistema de Views

Durante más de diez años, una pantalla de Android se construía en dos partes:

- Un fichero **XML** con el *layout*: qué widgets hay (`TextView`, `Button`, `ImageView`…) y cómo se colocan.
- Código **Kotlin/Java** en la `Activity` o el `Fragment` que busca esos widgets por su id y los modifica a mano cuando cambian los datos.

Por ejemplo, un contador que muestra cuántas veces se ha pulsado un botón:

Fichero *xml* que define la interfaz gráfica:

```xml
<!-- res/layout/activity_main.xml -->
<LinearLayout
    android:layout_width="match_parent"
    android:layout_height="match_parent"
    android:orientation="vertical">

    <TextView
        android:id="@+id/tvContador"
        android:layout_width="wrap_content"
        android:layout_height="wrap_content"
        android:text="Pulsado 0 veces" />

    <Button
        android:id="@+id/btnPulsar"
        android:layout_width="wrap_content"
        android:layout_height="wrap_content"
        android:text="Pulsa" />
</LinearLayout>
```

Fichero *Java* (o *Kotlin*) que define la lógica de la pantalla:

```kotlin
// MainActivity.kt
val tvContador = findViewById<TextView>(R.id.tvContador)
val btnPulsar = findViewById<Button>(R.id.btnPulsar)
var count = 0

btnPulsar.setOnClickListener {
    count++
    tvContador.text = "Pulsado $count veces" // si se te olvida esta línea, la pantalla miente
}
```

### Qué problemas tenía

- **Dos lenguajes para una sola pantalla.** El XML y el código Kotlin hay que mantenerlos sincronizados a mano: renombras un id y algo se rompe.
- **Actualizar la pantalla es responsabilidad tuya.** Cada vez que cambia un dato tienes que acordarte de actualizar *todos* los widgets que dependen de él. Con pantallas grandes es fácil que la interfaz acabe mostrando algo que no se corresponde con los datos: es la fuente de bugs más típica de las apps con Views.
- **Mucho código repetitivo.** Mostrar una simple lista exige un `RecyclerView` con su `Adapter` y su `ViewHolder`; crear un componente propio reutilizable supone heredar de `View` y lidiar con XML de atributos.
- **Atado a la versión de Android.** Las Views forman parte del propio sistema operativo, así que las mejoras y correcciones llegaban con cada versión de Android y los móviles antiguos se quedaban sin ellas.

### Jetpack Compose

Compose se presentó en 2019 y su versión estable (1.0) salió en julio de 2021. Resuelve esos problemas cambiando el planteamiento:

- **Todo es Kotlin.** La interfaz se escribe con funciones marcadas con `@Composable`; no hay XML de layouts.
- **La interfaz se describe a partir del estado.** No modificas widgets: dices *qué* debe verse para unos datos concretos y, cuando los datos cambian, Compose vuelve a pintar automáticamente lo que haga falta (a esto lo llama **recomposición**). Se suele resumir como **UI = f(estado)**, y es lo que se conoce como **interfaz declarativa**, frente a la **imperativa** de Views, donde das las órdenes de cambio paso a paso.
- **Es una biblioteca, no parte del sistema.** Va dentro de tu app como cualquier otra dependencia de Jetpack, se actualiza a su ritmo y funciona igual en móviles antiguos.

El mismo contador en Compose:

```kotlin
@Composable
fun Contador() {
    var count by remember { mutableStateOf(0) }

    Column {
        Text("Pulsado $count veces")
        Button(onClick = { count++ }) {
            Text("Pulsa")
        }
    }
}
```

Fíjate en que en `onClick` solo se cambia `count`; nadie toca el `Text`. Como el texto se *describe* a partir de `count`, es imposible que se quede desactualizado. Lo de `remember` y `mutableStateOf` lo veremos con calma más adelante; por ahora basta con saber que marcan `count` como **estado** que Compose vigila.

| | Views (clásico) | Jetpack Compose |
| :--- | :--- | :--- |
| **Lenguaje** | XML + Kotlin/Java | Solo Kotlin |
| **Cuando cambian los datos** | Actualizas cada widget a mano | Cambias el estado y Compose repinta |
| **Listas** | `RecyclerView` + `Adapter` + `ViewHolder` | `LazyColumn` |
| **Actualizaciones** | Con cada versión de Android | Como cualquier biblioteca |

Compose no es perfecto. Que sea una biblioteca más (la última fila de la tabla) tiene su contrapartida: tu proyecto depende de muchas piezas cuyas versiones tienen que encajar entre sí. Están Kotlin, el Android Gradle Plugin (AGP), el `compileSdk` y las propias librerías de AndroidX, y además cada versión de Android Studio solo admite AGP hasta cierta versión. Cuando una pieza se adelanta o se queda atrás aparece el temido *dependency hell*, y encontrar una combinación que compile puede costar. Ya lo hemos sufrido juntos en el aula, quienes habéis estado conmigo en presencial. Para suavizarlo existe el **Compose BOM**: con una sola versión alinea todas las librerías de Compose, y lo verás en el `build.gradle.kts` de cualquier proyecto nuevo. Pero subir la versión del BOM tampoco es inocuo: entre las versiones de 2025 y 2026, por ejemplo, el código que usaba el composable `Icon` dejó de compilar. El problema se agrava con las librerías de terceros, que a menudo tardan en adaptarse y cuyas actualizaciones pueden romper código que ya funcionaba.

### ¿Entonces Views ha muerto?

No del todo. Google recomienda Compose para cualquier app nueva y todo lo nuevo nace ahí: los componentes de Material 3, las APIs de Wear OS, TV o widgets, los ejemplos de la documentación y los *codelabs*. El sistema de Views ha pasado a ser **legacy**: se mantiene, pero ya no evoluciona.

Eso sí, hay muchísimas apps en producción escritas con Views, así que en una empresa es muy probable que te toque mantener o migrar código de este tipo. Ambos sistemas pueden convivir en la misma app (Compose dentro de Views y al revés), lo que permite migrar pantalla a pantalla. Si alguna vez ves `findViewById`, un `RecyclerView` o una carpeta `res/layout` llena de XML, ya sabes de dónde viene.

> [!NOTE]
> En este curso trabajaremos exclusivamente con Compose. Cuando busques ayuda en internet, ten cuidado: muchas respuestas antiguas (y algunas de la IA) dan soluciones con Views que no te sirven.

### Qué hay en `MainActivity`

Este es el código que nos genera la plantilla:

```kotlin
class MainActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        enableEdgeToEdge()
        setContent {
            T03ej1Theme {
                Scaffold(modifier = Modifier.fillMaxSize()) { innerPadding ->
                    Greeting(
                        name = "Android",
                        modifier = Modifier.padding(innerPadding)
                    )
                }
            }
        }
    }
}
```

`MainActivity.kt` es el **fichero** de entrada de la app cuando usamos la plantilla. Recuerda que en Kotlin la clase no tiene por qué llamarse como el fichero y que en un fichero podemos tener varias clases, funciones, etc. Dentro tiene una **clase**, `MainActivity`, que hereda de `ComponentActivity`. Una *Activity* es una pantalla de la app; al heredar de `ComponentActivity` nuestra clase recibe todo lo necesario para que Android la gestione y, además, el método `setContent` para pintar su interfaz con Compose.

Dentro de la clase tenemos el método `onCreate()`, que es el punto de entrada de la app, el equivalente al `main()` de Kotlin: al lanzarse la app se ejecuta el `onCreate()` de `MainActivity`. `onCreate()` es un evento del ciclo de vida de la app (*lifecycle*), que estudiaremos con algo más de detalle más adelante en el curso.

Dentro de este método se llama a `setContent()`, que es el punto en el que la app está preparada para recibir la UI con funciones *composables*.

Una **función Composable** es la herramienta clave del paradigma declarativo de Jetpack Compose. Es una función normal de Kotlin con la anotación `@Composable` delante, que le dice al compilador que Compose la usa para generar UI. Su nombre va con mayúscula y **no devuelve nada** (`Unit`): no "retorna" un texto o un botón, sino que *emite* UI. Recibe los datos por parámetros y puede llamar a otros Composables, así que la interfaz acaba siendo un **árbol de funciones**. Por ejemplo, la función `Greeting()` es un Composable que recibe un parámetro `name` y muestra un texto con ese nombre.

Más abajo tenemos:

- `T03ej1Theme`: define el tema de la app, con colores, tipografía y formas. Lo veremos más adelante en el curso.
- `Scaffold`: es un contenedor que define la estructura básica de una pantalla. A través de su lambda pasa a los Composables hijos el parámetro `innerPadding`, que permite que el contenido no quede debajo de la barra de estado ni de la barra de navegación. Se lo iremos pasando en el `modifier` de los Composables hijos.

Esa es la estructura básica de una app con Jetpack Compose, y la parte que en general no tocamos.

### Tu primer Composable

Ahora vamos a hacer tabula rasa: borramos los Composables que vienen por defecto (`Greeting` y `GreetingPreview`) y creamos uno nuestro.

![MainActivity con el Scaffold vacío tras borrar Greeting](img/T03/mainactivity-scaffold-vacio.png)

Creamos nuestro Composable `HelloWorldComposable` y su *preview* `HelloWorldComposablePreview`, que nos permite ver el Composable sin compilar la app entera. Añadir `Preview` al nombre del Composable es una convención que nos permite identificarlo fácilmente.

![Funciones HelloWorldComposable y HelloWorldComposablePreview recién creadas y vacías](img/T03/helloworld-composable-y-preview-vacios.png)

Actualizamos la firma: no queremos *hardcodear* el texto, sino que se le pueda pasar como parámetro. Por eso añadimos un parámetro `text` de tipo `String`.

Fíjate también en el parámetro opcional `modifier` de tipo `Modifier`. El `Modifier` es un objeto que nos permite aumentar o decorar un Composable: añadirle un *padding*, un borde, un fondo, una sombra, etc. Se pasa como parámetro y se pueden encadenar varias modificaciones. Es (aproximadamente) como el `css` de la web, pero en Kotlin.

Es **el patrón estándar de Compose**: todo Composable reutilizable acepta un `modifier: Modifier = Modifier` como **primer parámetro opcional** y se lo pasa a su primer hijo. Así quien lo usa puede decidir márgenes, tamaño, alineación… desde fuera, sin tocar su código. Lo verás en todos los ejercicios del curso.

![Firma de HelloWorldComposable con los parámetros text y modifier](img/T03/helloworld-firma-parametros.png)

Nuestro Composable es básicamente un *wrapper* de un `Text`, el Composable que pinta texto en la pantalla. Lo normal es que un Composable propio anide varios, pero en este punto tan introductorio nos quedamos solo con el `Text`, aunque no tenga excesivo sentido.

![HelloWorldComposable con un Text que recibe text y modifier](img/T03/helloworld-text.png)

Fíjate en cómo pasamos el `modifier` que nos llega como parámetro al `Text`.

Hora de montar la *preview*. Primero le pasamos a la anotación `@Preview` los parámetros `showBackground = true`, para que muestre un fondo, y `showSystemUi = true`, para que muestre la barra de estado y la barra de navegación. Así vemos el Composable tal y como se verá en el móvil.

![Anotación @Preview con showBackground y showSystemUi a true](img/T03/preview-showbackground-showsystemui.png)

Replicamos dentro la estructura con el `Theme` y el `Scaffold` que teníamos en `MainActivity`. Así vemos el Composable dentro del contexto de la app, con su tema y su estructura básica.

![HelloWorldComposablePreview con T03ej1Theme, Scaffold y HelloWorldComposable con el texto Hello, World!](img/T03/preview-theme-scaffold.png)

En modo *Split* ya podemos ver el resultado en la *preview*, con el texto que le hemos pasado como parámetro.

![Preview de HelloWorldComposablePreview mostrando Hello, World! bajo la barra de estado](img/T03/preview-hello-world.png)

La *preview* es muy útil para ir viendo los cambios que hacemos en el Composable en tiempo real: el emulador de Android es muy pesado y tarda mucho en arrancar.

Por último, montamos esto mismo en `MainActivity` para que se vea en el emulador o en el móvil: dentro del `setContent` llamamos a `HelloWorldComposable` y le pasamos el texto que queremos mostrar.

![MainActivity llamando a HelloWorldComposable dentro del Scaffold](img/T03/mainactivity-llama-helloworld.png)

### Cambiar el color de fondo con `Surface`

Para cambiar el color de fondo usaremos el Composable `Surface`, un contenedor canónico para modificar borde, color de fondo, etc.

Para envolver nuestro Composable con él: selecciónalo, pulsa `Alt + Enter` -> **Surround with widget** -> **Surround with Container** y cambia el `Box` que genera por `Surface`.

![Menú de Alt+Enter con la opción Surround with widget seleccionada](img/T03/surround-with-widget.png)

Al meter el `Surface`, que será el contenedor visual, tenemos que mover a él el `modifier` que antes le pasábamos a nuestro Composable, para que el *padding* se aplique al contenedor. Si no, el *padding* se aplicaría solo al texto (o dos veces, si lo dejamos en ambos sitios) y el resultado visual sería diferente.

![MainActivity con un Surface que recibe Modifier.padding(innerPadding) y envuelve al Composable](img/T03/surface-en-mainactivity.png)

`Surface` tiene un parámetro `color` para cambiar el color de fondo:

![Firma de Surface con sus parámetros modifier, shape, color, contentColor, tonalElevation, shadowElevation, border y content](img/T03/firma-surface.png)

Para indicar el color usamos la clase `Color`, que permite definir colores en diferentes formatos (RGB, ARGB, etc.). Al escribir `Color` verás que el IDE nos sugiere bastantes opciones para autoimportar. Habitualmente la buena es la primera, pero no siempre: esto requiere un poco de experiencia, atención o consultar la documentación. En este caso nos interesa `androidx.compose.ui.graphics.Color` (¡no `android.graphics.Color`!). Si no se ha importado, `Alt + Enter` lo importa automáticamente.

![Autocompletado de Color con varias opciones de androidx.compose.ui.graphics y android.graphics](img/T03/autocompletado-color.png)

Borramos los paréntesis que nos habrá autocompletado, ponemos el punto y escribimos `Cyan`; el autocompletado sugiere los colores al escribir el punto tras `Color`. El resultado final es `color = Color.Cyan`.

Es buen momento para usar **Optimize Imports** (`Ctrl + Alt + O`) y mantener los imports ordenados y sin restos. Equivale a desplegar la lista de imports y borrar a mano los que no se usan (los que aparecen en gris).

![Lista de imports con androidx.compose.foundation.layout.Box en gris porque ya no se usa](img/T03/imports-sin-usar.png)

> [!WARNING]
> **Lo que pongas en la *preview* no aparece en la app, y al revés.** Prueba ahora a comparar: la *preview* sigue mostrando el texto sin fondo, pero si lanzas la app en el emulador sí verás el fondo cyan. La *preview* muestra la función que tiene la anotación `@Preview`, y el emulador lo que lance `onCreate()` en `MainActivity`; como el `Surface` solo lo hemos puesto en `MainActivity`, no coinciden. Es el error típico número 1: "he cambiado el texto y en el móvil no sale".

### Añadir un `padding`

Un *padding* es un espacio entre el contenido de un Composable y su borde. Nos permite separar visualmente el contenido y mejorar la legibilidad y la estética de la interfaz.

![Diagrama de un Surface con un Modifier.padding de 16.dp fuera del color de fondo y un Text con Modifier.padding de 24.dp dentro de él](img/T03/padding-compose.png)

Como ves en el diagrama, **dónde** pongas el *padding* importa: en el `modifier` del `Surface` queda fuera del fondo, y en el del `Text` queda dentro, pintado con el color del `Surface`.

Para aplicarlo usamos `Modifier.padding(24.dp)`, donde `dp` son píxeles independientes de la densidad (*density-independent pixels*), lo que permite que el *padding* se vea igual en pantallas con diferente resolución. Necesitarás dos imports nuevos: `padding` y `dp`.

Para terminar, mueve el `Surface` **dentro** de tu Composable. Es un lugar mejor para ponerlo y así la *preview* y `MainActivity` mostrarán lo mismo:

```kotlin
@Composable
fun HelloWorldComposable(
    text: String,
    modifier: Modifier = Modifier
) {
    Surface(
        color = Color.Cyan,
        modifier = modifier
    ) {
        Text(
            text = text,
            modifier = Modifier.padding(24.dp)
        )
    }
}
```

Siéntete libre de experimentar con otros colores y textos: cambia el fondo a `Color.Yellow` o `Color.Green`, usa el código hexadecimal de un color (`Color(0xFFBDE3D1)`; ojo, aquí el canal alfa va **delante**, no detrás) o cambia el texto a "Hola, soy *tu nombre*". Así verás cómo afecta cada cambio al resultado final.

Si sigues el *codelab* en lugar de esta guía, este es su resultado final, con el nombre "Meghan" y fondo cyan:

![Preview del codelab con el texto Hi, my name is Meghan! sobre fondo cyan](img/T03/Hello_Meghan.png)

## Ejercicio 2 (práctica guiada): textos, filas y columnas

*Práctica guiada, no se entrega.*

Basado en el *codelab* oficial [Compila una app simple con elementos de texto componibles](https://developer.android.com/codelabs/basic-android-kotlin-compose-text-composables). Aquí va lo esencial, reordenado y sin rodeos.

**Objetivo:** construir una tarjeta de felicitación ("Happy Birthday") que muestre un mensaje grande y una firma. En vez de Sam y Emma, como en el *codelab*, haz que aparezcan tu nombre y el de María. Feliz cumpleaños o *happy birthday*, cualquiera vale.

![Emulador mostrando la tarjeta del codelab: «Happy Birthday Sam!» en grande y «From Emma» debajo a la derecha](img/T03/tarjeta-happy-birthday-objetivo.png)

Crea un proyecto nuevo con la plantilla *Empty Activity*, llámalo `T03-ej2` (paquete `net.iessochoa.tunombre.t03_ej2`) y deja el *Minimum SDK* en API 26, como en el ejercicio anterior.

> [!TIP]
> Aquí se usan sin parar cosas de Kotlin que ya conocéis de T02: **parámetros con valor por defecto**, **argumentos con nombre** y **string templates** (`$name`).

### Anotaciones: `@Composable` y `@Preview`

Una anotación es metainformación que se pega al código con `@`. Puede llevar parámetros.

| Anotación | Para qué sirve |
|---|---|
| `@Composable` | "Esta función genera UI". Obligatoria en todo Composable. |
| `@Preview` | "Pinta esta función en el panel *Design* de Android Studio". |
| `@Preview(showBackground = true)` | Igual, pero con fondo blanco. |
| `@Preview(showBackground = true, showSystemUi = true)` | Muestra además el marco del móvil (barra de estado, etc.). |

Una función con `@Preview` **no puede tener parámetros obligatorios** (¿de dónde sacaría Android Studio el valor?). Por eso el patrón es una función "de verdad" con parámetros y una *preview* sin ellos que la llama con datos de ejemplo:

```kotlin
@Composable
fun GreetingText(message: String, from: String) { ... }   // la de verdad

@Preview(showBackground = true)
@Composable
fun BirthdayCardPreview() {                                // solo para mirar
    T03ej2Theme {
        GreetingText(message = "Happy Birthday Maria!", from = "From Sergio")
    }
}
```

### Cómo se llaman los Composables

Convención oficial: **PascalCase y sustantivo** (es un *elemento* de la UI, no una acción).

| ✅ Bien | ❌ Mal | Por qué está mal |
|---|---|---|
| `FancyButton()` | `fancyButton()` | No es PascalCase |
| `RoundIcon()` | `RenderFancyButton()` | Es un verbo |
| `BackButtonHandler()` | `drawProfileImage()` | Ni PascalCase ni sustantivo |

Fijaos en que esto rompe la convención habitual de Kotlin (funciones en camelCase). Es a propósito: así se distingue a simple vista qué funciones son UI.

### Un texto grande: `sp` y `dp`

Borrad la función `Greeting` y sus llamadas (en `onCreate` y en la *preview*) y renombrad la *preview* a `BirthdayCardPreview`. Después creamos `GreetingText` siguiendo el patrón del `modifier` que vimos en el Ejercicio 1:

```kotlin
@Composable
fun GreetingText(message: String, modifier: Modifier = Modifier) {
    Text(
        text = message,
        fontSize = 100.sp,
        lineHeight = 116.sp,
        modifier = modifier
    )
}
```

- **`sp`** (*scale-independent pixels*): unidad para **texto**. Se escala con el tamaño de fuente que el usuario elige en los ajustes del móvil (accesibilidad).
- **`dp`** (*density-independent pixels*): unidad para **todo lo demás** (márgenes, tamaños, *padding*).
- `100.sp` es una *propiedad de extensión* sobre `Int` (también funciona con `Float` y `Double`). Necesita `import androidx.compose.ui.unit.sp` -> `Alt + Enter` sobre lo rojo.
- Si la letra es enorme y las líneas se pisan, falta `lineHeight`.

Ahora añadimos el segundo texto, la firma:

```kotlin
@Composable
fun GreetingText(message: String, from: String, modifier: Modifier = Modifier) {
    Text(text = message, fontSize = 100.sp, lineHeight = 116.sp, modifier = modifier)
    Text(text = from, fontSize = 36.sp)
}
```

Resultado: **los dos textos salen uno encima del otro, superpuestos.** Compose no sabe cómo colocarlos porque no se lo hemos dicho. Esto lleva a lo más importante de la práctica 👇

![Vista previa con «from Sergio» y «Happy Birthday!» superpuestos en la esquina superior izquierda](img/T03/textos-superpuestos-sin-layout.png)

### Layouts: `Row`, `Column` y `Box`

A continuación teneis una infografía que explica los contenedores que se utilizan para organizar el layout de sus Composables hijos. `Row` organiza a sus hijos en horizontal, `Column` en vertical y `Box` los apila unos encima de otros.

![Infografía de Column, Row y Box: cómo colocan a sus hijos (vertical, horizontal y apilados) y la sintaxis trailing lambda](img/T03/infografia-column-row-box.png)

#### Aplicado a la tarjeta

Con `Row` el mensaje y la firma ya no se pisan, pero la firma se queda sin sitio. Lo que queremos es `Column`, y el `modifier` pasa del `Text` a la `Column`, que ahora es el primer hijo:

```kotlin
@Composable
fun GreetingText(message: String, from: String, modifier: Modifier = Modifier) {
    Column(modifier = modifier) {
        Text(text = message, fontSize = 100.sp, lineHeight = 116.sp)
        Text(text = from, fontSize = 36.sp)
    }
}
```

### Llevarlo a la app y alinear

Desde `onCreate`, dentro del `Scaffold`, llamamos a `GreetingText` pasándole el `innerPadding` (en el *codelab* aparece un `Surface` porque usa la plantilla antigua; es el paso que allí llaman **Adopt good practice**):

```kotlin
T03ej2Theme {
    Scaffold(modifier = Modifier.fillMaxSize()) { innerPadding ->
        GreetingText(
            message = "Happy Birthday Maria!",
            from = "From Sergio",
            modifier = Modifier.padding(innerPadding)
        )
    }
}
```

Ejecutad en el emulador. **Ahora sí** se ve en la app. Recordad la diferencia entre lo que aparece en la *preview* y lo que se muestra en el emulador:

![Comparación entre la preview y el emulador del ejercicio 2](img/T03/preview_avd.png)

No coinciden porque la *preview* y `onCreate` montan cosas distintas: una llama a `GreetingText` a pelo y la otra lo mete en un `Scaffold`. La solución es tener **un único Composable raíz** con el tema y el `Scaffold`, y llamarlo desde los dos sitios:

```kotlin
@Composable
fun BirthdayApp() {
    T03ej2Theme {
        Scaffold(modifier = Modifier.fillMaxSize()) { innerPadding ->
            GreetingText(
                message = "Happy Birthday Maria!",
                from = "From Sergio",
                modifier = Modifier.padding(innerPadding)
            )
        }
    }
}

@Preview(showBackground = true, showSystemUi = true)
@Composable
fun BirthdayCardPreview() {
    BirthdayApp()
}
```

Y en `MainActivity` el `setContent` se queda en una línea:

```kotlin
setContent {
    BirthdayApp()
}
```

Ahora la *preview* y el emulador pintan exactamente lo mismo: si cambias algo en `BirthdayApp`, lo ves en los dos sitios. Acostumbraos a este patrón (`XxxApp()` llamado desde `setContent` y desde la *preview*), porque lo vamos a repetir en todos los proyectos. 

>[!NOTE]
> El `showSystemUi` tiene un defecto y es que aplica su `innerPadding` con un valor de 0, así que la *preview* no refleja exactamente lo que se ve en el emulador. En este punto hay dos opciones, quitar el `showSystemUi` de la *preview* o dejarlo, hacer que `BirthdayApp()` pueda recibir un parámetro `modifier` opcional y pasarle un `padding(top = 24.dp)` desde la *preview*. Aquí a gusto del consumidor, pero lo importante es que la *preview* y el emulador pinten lo mismo.

Ahora toca centrar y alinear. Para la alineación del texto dentro de su propio bloque usamos `textAlign = TextAlign.Center`. Para centrar el bloque en la pantalla usamos `verticalArrangement = Arrangement.Center` en la `Column`. Y para alinear la firma a la derecha usamos `Modifier.align(Alignment.End)` en el segundo `Text`.

```kotlin
@Composable
fun GreetingText(message: String, from: String, modifier: Modifier = Modifier) {
    Column(
        verticalArrangement = Arrangement.Center,   // centra el bloque en vertical
        modifier = modifier
    ) {
        Text(
            text = message,
            fontSize = 100.sp,
            lineHeight = 116.sp,
            textAlign = TextAlign.Center            // centra el texto dentro de sí mismo
        )
        Text(
            text = from,
            fontSize = 36.sp,
            modifier = Modifier
                .padding(16.dp)
                .align(alignment = Alignment.End)   // este hijo, a la derecha
        )
    }
}
```

Si lo ejecutáis así, **el bloque no se centra**. `verticalArrangement` reparte los hijos dentro del espacio que ocupa la `Column`, y la `Column` solo mide lo que miden sus dos textos, así que no hay sitio sobrante que repartir. El `fillMaxSize()` del `Scaffold` no se hereda: el `Scaffold` deja que su contenido mida lo que necesite.

Para que el bloque quede centrado en toda la pantalla, la `Column` tiene que ocuparla entera. Se lo pedimos desde la llamada en `BirthdayApp`:

```kotlin
GreetingText(
    message = "Happy Birthday Maria!",
    from = "From Sergio",
    modifier = Modifier
        .fillMaxSize()
        .padding(innerPadding)
)
```

> [!NOTE]
> En el *codelab* esto no hace falta porque usa la plantilla antigua, con un `Surface(modifier = Modifier.fillMaxSize())`. El `Surface` obliga a su hijo a ocupar todo su tamaño; el `Scaffold` de la plantilla nueva no.

Tres formas distintas de "alinear", que conviene no confundir:

| Qué | Dónde se pone | Afecta a |
|---|---|---|
| `verticalArrangement` | parámetro de `Column` | cómo se reparten **todos** los hijos en el eje principal |
| `textAlign` | parámetro de `Text` | cómo se alinean las letras **dentro** de ese texto |
| `Modifier.align(...)` | modifier de **un hijo** | dónde se coloca **ese** hijo dentro de la columna |

Buenas prácticas que aparecen de paso:

- *Padding* en múltiplos de **4.dp** (8, 16, 24…).
- Los modifiers se **encadenan** con `.` (`.padding(16.dp).align(...)`), y el orden importa (lo veremos en el Ejercicio 3). A mi me gusta separarlo en varias líneas para que se vea mejor.
- El *padding* "externo" de un componente mejor pasarlo desde el padre (en la llamada), no fijarlo dentro.

<img src="img/T03/ejercicio2_avd.png" alt="Ejercicio 2 en el emulador: felicitación de cumpleaños centrada con la firma alineada a la derecha" width="30%">

### Errores típicos

Algunas cuestiones qe os podéis encontrar durante la reaalización de esta práctica.

1. **"He cambiado el texto y en el móvil no sale"** -> lo cambiaste en la *preview*, no en `onCreate`.
2. **La *preview* no aparece** -> la función `@Preview` tiene parámetros sin valor por defecto, o falta `@Composable`.
3. **`.sp` / `.dp` / `Column` en rojo** -> falta el import. `Alt + Enter`.
4. **Textos superpuestos** -> varios Composables sin contenedor. Metedlos en `Column`/`Row`.
5. **Letras gigantes que se pisan** -> falta `lineHeight`.
6. **El texto queda debajo de la barra de estado** -> no estás usando el `innerPadding` del `Scaffold`.

### Resumen

- La UI en Compose = funciones `@Composable` que no devuelven nada.
- `@Preview` sirve para ver la UI en el IDE; no afecta a la app.
- Nombres de Composables: PascalCase y sustantivo.
- Texto en `sp`, todo lo demás en `dp`.
- `Column` (vertical), `Row` (horizontal), `Box` (apilado) organizan a los hijos.
- Patrón obligatorio: `modifier: Modifier = Modifier` como parámetro y pasado al primer hijo.

*Práctica guiada, no se entrega.*

Basado en el *codelab* oficial [Agrega imágenes a tu app para Android](https://developer.android.com/codelabs/basic-android-kotlin-compose-add-images). Continúa la tarjeta del Ejercicio 2.

**Objetivo:** poner una foto de fondo a pantalla completa detrás de la tarjeta de felicitación y, de paso, aprender a trabajar bien con **recursos** (imágenes y textos) en lugar de meterlo todo en el código.

Crea un nuevo proyecto llamado `T03-ej3` (paquete `net.iessochoa.tunombre.t03_ej3`) y copia en él el código del Ejercicio 2. Asegúrate de reemplazar los literales que contengan `t03_ej2` -> `t03_ej3` y `T03ej2` -> `T03ej3` (deberían ser unos 5 reemplazos).

<img src="img/T03/ejercicio3_preview.png" alt="Preview del ejercicio 3: la felicitación de cumpleaños sobre una imagen de fondo" width="30%">

### Qué es un recurso

Un **recurso** es cualquier contenido estático que usa la app y que **no es código**: imágenes, textos, colores, iconos, animaciones… Viven en la carpeta `res/`, cada tipo en su subcarpeta:

```text
app/src/main/
├── java/.../MainActivity.kt      ← código
└── res/                          ← recursos
    ├── drawable/                 ← imágenes y gráficos
    ├── drawable-nodpi/           ← imágenes que Android NO debe reescalar
    ├── mipmap/                   ← icono de la app (launcher)
    └── values/
        └── strings.xml           ← textos
```

¿Por qué separarlos del código?

- **Traducción:** Android elige solo `values-es/strings.xml` o `values-en/strings.xml` según el idioma del móvil.
- **Adaptación al dispositivo:** puede elegir una imagen u otra según la densidad de pantalla, la orientación, el modo oscuro…
- **Mantenimiento:** cambias un texto en un sitio y se actualiza en toda la app.

#### La clase `R`

Android genera automáticamente una clase `R` con un **ID numérico para cada recurso**. El ID se llama igual que el fichero (sin extensión):

| Fichero | Cómo se referencia en código |
|---|---|
| `res/drawable/androidparty.png` | `R.drawable.androidparty` |
| `<string name="signature_text">` en `strings.xml` | `R.string.signature_text` |

> [!WARNING]
> Los nombres de recursos van **en minúsculas y con guiones bajos** (`happy_birthday_text`). Nada de mayúsculas, espacios ni guiones medios: si no, `R` no compila.

![Icono del Resource Manager resaltado en la barra lateral izquierda de Android Studio, bajo el de Project](img/T03/boton-resource-manager.png)

3. **+ -> Import Drawables** -> elegid el fichero.

![Menú del botón + del Resource Manager con la opción Import Drawables seleccionada](img/T03/import-drawables.png)

4. En **Qualifier type** elegid **Density** y en **Value** elegid **No Density** -> *Next* -> *Import*.

¿Por qué *No Density*? Hay móviles con ~160 píxeles por pulgada y otros con ~480. Si no le dices nada, Android **reescala** las imágenes para adaptarlas a cada densidad, y con una foto grande eso puede dar imágenes borrosas, mucho consumo de memoria o directamente un `OutOfMemoryError`. > [!TIP]
> Regla rápida: iconos y gráficos pequeños -> `drawable` (o mejor, vectoriales). Fotos grandes de fondo -> `drawable-nodpi`.

### El Composable `Image`

Vamos a crear un nuevo fichero `GreetingImage.kt` y escribir en este el Composable que se encarga de pintar el fondo de la tarjeta. Aprovechamos de paso y lo creamos sobre el *package* de `ui` y no en `ui.theme`, que es solo para el tema. Para esto hay que hacer un poco de truco, crearlo primero en `ui.theme` y luego moverlo a `ui` con *Refactor -> Move*.

![Animación creando GreetingImage.kt en ui.theme y moviéndolo al paquete ui con Refactor -> Move](img/T03/mover-fichero-a-paquete-ui.gif)

Vamos ahora al ajo. Igual que `Text` pinta texto, `Image` pinta imágenes. Se hace en dos pasos:

```kotlin
@Composable
fun GreetingImage(message: String, from: String, modifier: Modifier = Modifier) {
    val image = painterResource(R.drawable.androidparty)   // 1. cargar el recurso
    Image(
        painter = image,                                    // 2. pintarlo
        contentDescription = null
    )
}
```

- `painterResource(id)` carga el drawable y devuelve un `Painter` (el objeto que sabe dibujarlo).
- Imports que pedirá Android Studio (`Alt + Enter`): `androidx.compose.ui.res.painterResource` y `androidx.compose.foundation.Image`.

El import de `R` tiene un poco de truco, porque es un nombre que se utiliza mucho en Android. Aseguraos de que el que se importa es el **del paquete de vuestra app**, no otro. Si no, `R.drawable.androidparty` sale en rojo.

![Lista de imports de R en Android Studio con la opción del paquete de la app (net.iessochoa...t03_ej3) resaltada](img/T03/import-r-paquete-app.png)

#### `contentDescription` es obligatorio (aunque sea `null`)

Es el texto que lee **TalkBack** (el lector de pantalla de Android) a personas con discapacidad visual. Si no lo ponéis, verás el error *"None of the following functions can be called with the arguments provided"*: no es opcional, aunque puede ser `null` si la imagen es puramente decorativa. En este caso, como es un fondo, lo ponemos a `null`:

![Firma de la función Image con el parámetro contentDescription: String? resaltado](img/T03/firma-image-contentdescription.png)

| Tipo de imagen | `contentDescription` |
|---|---|
| Aporta información (foto de producto, icono de "borrar"…) | Una descripción útil: `"Borrar mensaje"` (y mejor como recurso de string) |
| **Puramente decorativa** (como nuestro fondo) | `null` -> TalkBack la ignora |

Poner una descripción a algo decorativo **empeora** la accesibilidad: obliga al usuario a escuchar ruido.

### `Box`: apilar elementos

En el Ejercicio 2 vimos `Column` y `Row`. Ahora toca el tercero:

En un `Box` **el orden importa**: el primer hijo queda al fondo y cada uno de los siguientes se pinta encima del anterior. Es lo que necesitamos para poner texto sobre una foto.

> [!TIP]
> Box es una caja donde lanzas los Composables de arriba a abajo, el último que tiras queda por tanto encima, como ocurriría en una caja.

```kotlin
@Composable
fun GreetingImage(message: String, from: String, modifier: Modifier = Modifier) {
    val image = painterResource(R.drawable.androidparty)
    Box(modifier) {                       // patrón: el modifier va al primer hijo
        Image(
            painter = image,
            contentDescription = null
        )
        GreetingText(                     // reutilizamos lo del Ejercicio 2
            message = message,
            from = from,
            modifier = Modifier
                .fillMaxSize()
                .padding(8.dp)
        )
    }
}
```

Fijaos en la **composición**: `GreetingImage` no repite el código de los textos, llama a `GreetingText`. Los Composables se construyen unos con otros, como piezas de Lego.

Después, cambiad la *preview* y `onCreate` para que llamen a `GreetingImage` en lugar de `GreetingText`.

> [!NOTE]
> **Con la plantilla actual (`Scaffold` + *edge-to-edge*):** si le pasáis `Modifier.padding(innerPadding)` a `GreetingImage`, la foto no llegará a ocupar la zona de la barra de estado. Para un fondo a pantalla completa queda mejor que la imagen ocupe todo y aplicar el `innerPadding` solo al texto. Para este ejercicio, cualquiera de las dos opciones vale.

### Ajustar la imagen: `contentScale` y `alpha`

Al principio la foto sale arriba del todo y deja un hueco blanco debajo. Lo arreglamos con:

```kotlin
Image(
    painter = image,
    contentDescription = null,
    contentScale = ContentScale.Crop,   // rellena todo el espacio, recortando lo que sobre
    alpha = 0.5F                        // 50 % de opacidad -> el texto se lee mejor
)
```

Los `ContentScale` más útiles:

| Valor | Qué hace | Cuándo usarlo |
|---|---|---|
| `Fit` (por defecto) | Cabe entera, mantiene la proporción, puede dejar huecos | Logos, imágenes que no se pueden cortar |
| `Crop` | Rellena todo manteniendo la proporción, recorta lo que sobra | **Fondos**, fotos de portada |
| `FillBounds` | Rellena todo **deformando** la imagen | Casi nunca (se ve estirada) |
| `Inside` | Como `Fit`, pero nunca la agranda | Imágenes pequeñas que no queréis pixelar |

`alpha` va de `0F` (invisible) a `1F` (opaca). La `F` indica que el número es un `Float` (lo vimos en T02). También puede ser una `f` (minúscula).

### Modifiers más a fondo

Ya sabéis que un **Modifier** decora o cambia el comportamiento de un Composable (tamaño, márgenes, fondo, clics…) y que se **encadenan** con `.`. Lo importante ahora es que **se aplican en orden**, igual que veíamos con el *padding* del `Surface` en el Ejercicio 1:

```kotlin
Modifier
    .padding(16.dp)
    .background(Color.Green)   // margen fuera, el verde solo detrás del texto 
Modifier.background(Color.Green).padding(16.dp)   // el verde incluye también el relleno
```

Probad las dos en la *preview*: es la forma más rápida de entenderlo.

#### Padding por lados

```kotlin
Modifier.padding(16.dp)                                   // los cuatro lados
Modifier.padding(horizontal = 16.dp, vertical = 8.dp)
Modifier.padding(start = 16.dp, top = 16.dp, end = 16.dp, bottom = 16.dp)
```

Se usa `start`/`end` y no `left`/`right` porque en idiomas que se escriben de derecha a izquierda (árabe, hebreo) se invierte solo.

#### Arrangement y Alignment: eje principal y eje secundario

Esto es lo que más se lía, y es parecido al flexbox de CSS, así que en una tabla:

| | Eje **principal** -> `Arrangement` | Eje **secundario** -> `Alignment` |
|---|---|---|
| `Column` | `verticalArrangement` (arriba/abajo) | `horizontalAlignment` (izquierda/derecha) |
| `Row` | `horizontalArrangement` (izquierda/derecha) | `verticalAlignment` (arriba/abajo) |

- **Arrangement** = cómo se **reparten** los hijos en la dirección en la que se apilan. Solo tiene efecto si sobra espacio. Valores: `Top`/`Start`, `Center`, `Bottom`/`End`, `SpaceBetween`, `SpaceAround`, `SpaceEvenly`.
- **Alignment** = dónde se colocan los hijos en el **otro** eje: `Start`, `CenterHorizontally`, `End` (en `Column`), y `Top`, `CenterVertically`, `Bottom` (en `Row`).
- **`Modifier.align(...)`** sobre un hijo concreto **sobrescribe** el alignment del padre solo para ese hijo.

### Strings como recurso

Un texto escrito directamente en el código (*hardcoded*) no se puede traducir y hay que cambiarlo a mano en cada sitio donde aparece. Para extraerlo:

1. Seleccionad `Happy Birthday Maria!` (sin comillas) en `BirthdayApp`.
2. `Alt + Enter` -> **Extract string resource**.

![Animación seleccionando el texto, pulsando Alt + Enter y eligiendo Extract string resource](img/T03/extract-string-resource.gif)

3. *Resource name*: `happy_birthday_text` -> OK.
4. Repetid con la firma -> `signature_text`.

Resultado en `res/values/strings.xml`:

```xml
<resources>
    <string name="app_name">T03-ej3</string>
    <string name="happy_birthday_text">Happy Birthday Maria!</string>
    <string name="signature_text">From Sergio</string>
</resources>
```

Y en el código:

```kotlin
GreetingImage(
    message = stringResource(R.string.happy_birthday_text),
    from = stringResource(R.string.signature_text)
)
```

Fijaos en que hasta el nombre de la app (`app_name`) es un recurso de string.

![strings.xml con los recursos app_name, happy_birthday_text y signature_text](img/T03/strings-xml-recursos.png)

#### `getString()` vs `stringResource()`

A veces Android Studio genera `getString(R.string...)` al extraer. **Cambiadlo a `stringResource()`** (import: `androidx.compose.ui.res.stringResource`):

- `getString()` es un método de la `Activity`: funciona en `onCreate`, pero **no** dentro de un Composable cualquiera (ni en la *preview*).
- `stringResource()` es la versión Compose: funciona en cualquier `@Composable` y se actualiza si cambia la configuración (por ejemplo, el idioma).

### Errores típicos

1. **`Unresolved reference: androidparty`** -> la imagen no se importó, se llama distinto o el nombre tiene mayúsculas/guiones.
2. **"None of the following functions can be called…" en `Image`** -> falta `contentDescription`.
3. **La imagen deja un hueco blanco** -> falta `contentScale = ContentScale.Crop`.
4. **El texto queda *debajo* de la imagen y no se ve** -> en el `Box` habéis puesto el texto antes que la imagen. El orden importa.
5. **`getString` en rojo dentro de la *preview*** -> usad `stringResource`.
6. **Texto ilegible sobre la foto** -> bajad el `alpha` de la imagen.

### Resumen

- Los recursos (imágenes, textos…) van en `res/` y se referencian con `R.tipo.nombre`.
- Fotos grandes -> `drawable-nodpi`, para que Android no las reescale.
- `Image(painter = painterResource(...), contentDescription = ...)`; `null` si es decorativa.
- `Box` apila hijos: el primero al fondo.
- `contentScale` controla cómo se ajusta la imagen; `alpha`, su opacidad.
- Nada de textos a fuego: `strings.xml` + `stringResource()`.

### Iconos de contacto: `Icon`

`Icon` se parece mucho a `Image`, pero está pensado para iconos pequeños de un solo color: en lugar de pintar los colores originales, los **tiñe** con `tint` (por defecto, el color de contenido del tema). Así el icono cambia solo si cambias el tema o pasas a modo oscuro.

La pega es de dónde sacar el icono. Si copiáis el código del *codelab*, veréis que `Icons.Default.Phone` sale en rojo: la clase `Icons` vive en una librería aparte que los proyectos nuevos ya no incluyen. Es justo la rotura de `Icon` entre 2025 y 2026 de la que hablábamos al principio del tema. Hay tres caminos.

#### Opción 1 (recomendada): importar el icono como *Vector Asset*

Es lo mismo que hicisteis con la foto en el ejercicio 3, pero con una imagen vectorial:

1. En el **Resource Manager**: **+ -> Vector Asset**. (También vale botón derecho sobre `res` -> **New -> Vector Asset**.)
2. En *Clip art*, pulsad sobre el icono y buscad `phone`. Elegid el que más os guste.
3. Dadle un nombre, por ejemplo `ic_phone` -> *Next* -> *Finish*.
4. Comprobad que aparece `ic_phone.xml` en `res/drawable`.

![Menú del botón + del Resource Manager con la opción Vector Asset seleccionada](img/T03/resource-manager-vector-asset.png)

![Diálogo Configure Vector Asset con Asset type Clip art y el botón del icono de Clip art resaltado](img/T03/configure-vector-asset-clip-art.png)

![Diálogo Select Icon con la búsqueda phone y los iconos de teléfono disponibles](img/T03/select-icon-buscar-phone.png)

Y se usa con `painterResource`, igual que `Image`:

```kotlin
Icon(
    painter = painterResource(R.drawable.ic_phone),
    contentDescription = null, // el número de al lado ya dice que es un teléfono
    modifier = Modifier.size(24.dp),
    tint = MaterialTheme.colorScheme.primary
)
```

Recordad el truco del ejercicio 3: el `R` que hay que importar es el **del paquete de vuestra app**.

¿Por qué es la opción recomendada?

- **No añade dependencias**: no hay que tocar Gradle.
- El APK solo lleva **los iconos que usáis**, ni uno más.
- El `.xml` es un **vectorial**: se describe con formas, no con píxeles, así que se ve nítido a cualquier tamaño y en cualquier densidad de pantalla. Por eso va en `drawable` y no en `drawable-nodpi`.
- Es la vía que recomienda Google hoy para los iconos.

¿La pega? Hay que importarlos de uno en uno. Para los tres o cuatro de la tarjeta, eso no es nada.

#### Opción 2: la librería `material-icons-core`

Si preferís escribir `Icons.Default.Phone` como en el *codelab*, hay que añadir la librería al proyecto. En `gradle/libs.versions.toml`, dentro de `[libraries]`:

```toml
androidx-compose-material-icons-core = { group = "androidx.compose.material", name = "material-icons-core" }
```

No lleva versión porque la pone el **Compose BOM**. Si al sincronizar Gradle se queja de que falta, añadid `version = "1.7.8"`.

> [!NOTE]
> Las versiones se comprueban [buscando en Maven Central](https://mvnrepository.com/artifact/androidx.compose.material/material-icons-core/versions). La última estable es la 1.7.8 para *material-icons-core*.

Y en `app/build.gradle.kts`, dentro de `dependencies`:

```kotlin
implementation(libs.androidx.compose.material.icons.core)
```

Pulsad **Sync Now** y ya funciona el código del *codelab* (imports `androidx.compose.material.icons.Icons` y `androidx.compose.material.icons.filled.Phone`):

```kotlin
Icon(
    imageVector = Icons.Default.Phone,
    contentDescription = null,
    modifier = Modifier.size(24.dp),
    tint = MaterialTheme.colorScheme.primary
)
```

- A favor: el autocompletado de `Icons.Default.` es muy cómodo y la librería es pequeña.
- En contra: solo trae un **conjunto básico** de unos 50 iconos (`Phone`, `Email`, `Share`, `Person`, `LocationOn`, `Home`…). Para la tarjeta sobra, pero en cuanto necesitéis algo menos común no estará. Además, Google **ya no la actualiza**: los *Material Icons* han dado paso a los *Material Symbols*.

#### Opción 3 (desaconsejada): `material-icons-extended`

Existe una versión "extendida" de la anterior con **todos** los iconos de Material (miles, en las variantes `Filled`, `Outlined`, `Rounded`, `Sharp` y `TwoTone`). Se añade igual que la opción 2, cambiando `material-icons-core` por `material-icons-extended`.

Para una prueba rápida y furiosa, en la que queréis un icono raro ya y sin pensar, es tentadora. Pero no la uséis en un proyecto de verdad:

- Es **enorme**: alarga bastante cada compilación.
- En *debug* no se aplica R8 (la herramienta que elimina el código que no se usa), así que **el APK engorda mucho** por unos pocos iconos.
- Igual que la `core`, está **congelada**: Google ya no la actualiza.

Si solo necesitáis un icono que no está en la `core`, la opción 1 os lo da sin ninguno de estos problemas.
