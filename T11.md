# T11 · Integración de APIs con Retrofit y Coroutines. Manejo de Intents en Android

## 1. El sistema de mensajería de Android: Intents

En el desarrollo nativo, los componentes de una aplicación (como las *Activities* o los *Services*) no se invocan directamente instanciando sus clases. Android utiliza un **sistema de mensajería asíncrona** llamado **Intent**. Un `Intent` es una descripción abstracta de una operación que se va a realizar.

Según el currículo oficial, debemos dominar las clases necesarias para la conexión y comunicación, y los Intents son la piedra angular para ello. Esta sección cubrirá los aspectos esenciales de los Intents en Android, no pretende ser un curso exhaustivo (como en casi todo hay mucho más y mejor), pero sí darte las bases para que puedas utilizarlos eficazmente en tus aplicaciones.

### 1.1. Tipos de Intents

Podemos clasificar los Intents en dos grandes grupos según su propósito y especificidad:

#### A. Intents Explícitos

Se utilizan para iniciar un componente específico dentro de tu propia aplicación. Se denominan "explícitos" porque defines exactamente qué clase (Activity o Service) quieres arrancar. Son la base de la navegación clásica en Android.

**Ejemplo: Navegar de la `MainActivity` a `DetailActivity`**

```kotlin
val intent = Intent(this, DetailActivity::class.java)
startActivity(intent)
```

> [!NOTE]
> Esto lo verás sobre todo si tienes la ¿suerte? de trabajar con proyectos legacy (view system / XML) o con código Java antiguo. En proyectos modernos con Jetpack (**Navigation Compose**), la navegación entre pantallas se gestiona con los Navigation Components que hemos visto (aunque los Intents explícitos siguen siendo válidos y útiles en muchos casos).

#### B. Intents Implícitos

No nombran un componente específico, sino que declaran una **acción general** a realizar. El sistema Android busca entre todas las aplicaciones instaladas aquellas que tengan un *Intent Filter* capaz de manejar dicha acción. Esto es crucial para integrar nuestra app con el ecosistema (abrir mapas, compartir texto, hacer una llamada, etc.).

Como imaginarás, estos Intents son fundamentales para nosotros a la hora de consumir los servicios de otras apps o del sistema.

**Ejemplo: mandar un texto:**

```kotlin
    // Acción: ENVIAR algo (SEND)
    val sendIntent = Intent(Intent.ACTION_SEND).apply {
        // Importante: Definir el tipo de dato (MIME type)
        type = "text/plain"
        // El contenido a compartir
        putExtra(Intent.EXTRA_TEXT, "¡Mira la nueva app del instituto! Descárgala aquí.")
    }

    // createChooser crea el menú visual para elegir app (WhatsApp, Gmail, etc.)
    // y además protege si no hay ninguna app (aunque es raro no tener ninguna).
    val shareIntent = Intent.createChooser(sendIntent, "Compartir vía...")
    context.startActivity(shareIntent)
```

#### C. Resumen de los tipos de Intents (TLDR)

Es importante aclarar la diferencia entre ambos tipos de Intents en función del contexto de uso, dado que la evolución de Android ha cambiado la forma en que navegamos entre pantallas. ¡Android evoluciona rapidísimo y hay que estar al día!  

**Navegación Interna (Dentro de tu App)**:

- En el pasado (Legacy/View System): Se usaban Intents Explícitos para saltar de una pantalla a otra (de Activity a Activity). Era pesado y lento.
- En el presente (Jetpack Compose): Usamos Navigation Compose. Google recomienda una arquitectura de "Activity Única" (Single Activity Architecture), donde la navegación entre pantallas se gestiona intercambiando funciones `@Composable` de forma fluida dentro de la misma ventana, sin usar Intents.

**Navegación Externa (Hacia otras Apps)**:

- Aquí los Intents (Implícitos) siguen siendo los reyes indiscutibles. Da igual que uses tecnología moderna o antigua; si quieres abrir la cámara, el mapa o compartir un texto con WhatsApp, necesitas un Intent.

### 1.2. Transferencia de datos entre Activities (Extras)

Un `Intent` puede transportar datos adicionales utilizando el método `putExtra()`, que funciona como un mapa de clave-valor. Estos datos se recuperan en la actividad de destino a través de `intent.extras`.

**Enviar datos:**

```kotlin
val intent = Intent(this, UserProfileActivity::class.java).apply {
    putExtra("USER_ID", 42)
    putExtra("USER_NAME", "Alice")
}
startActivity(intent)
```

**Recibir datos (en `UserProfileActivity`):**

```kotlin
val userId = intent.getIntExtra("USER_ID", -1) // -1 es el valor por defecto
val userName = intent.getStringExtra("USER_NAME")
```

### 1.3.2. Paso 1: Abrir Web (LocalUriHandler)

Empezamos con lo fácil. En **Jetpack Compose**, abrir una URL es trivial gracias a `LocalUriHandler`.
Sitúate al principio de la función `IESSeveroOchoaIntents()`, donde están las variables. Verás que ya tienes definido:

```kotlin
    val context = LocalContext.current
    val uriHandler = LocalUriHandler.current // El "mago" que abre enlaces
    val webUrl = "https://portal.edu.gva.es/03013224/"
```

- **¿Qué es `LocalUriHandler`?** Es una herramienta de Compose que sabe "despachar" URIs. Si le das una web, abre el navegador. Si le das un teléfono, abre el marcador.

Ahora, ve al botón **"Web del Instituto"** y en su `onClick` añade:

```kotlin
    uriHandler.openUri(webUrl)
```

¡Listo! Android detectará el prefijo `https://` y buscará un navegador (Chrome) para abrirlo.

### 1.3.3. Paso 2: Llamada Telefónica (El esquema `tel:`)

Continuamos con el botón de **Llamar**. Aquí vamos a usar el mismo `uriHandler`, pero el truco está en la cadena de texto que le pasamos.
Las URIs funcionan por **esquemas**.

- Web -> `https://...`
- Teléfono -> `tel:...`

Busca el botón **"Llamar a Secretaría"** y añade:

> **Detalle:** Fíjate en el prefijo `tel:`. Sin él, Android intentaría abrirlo como una web y fallaría.

### 1.3.4. Paso 3: Google Maps (Codificación y Query Strings)

Aquí la cosa se pone interesante. Queremos abrir Google Maps centrado en el instituto, con el zoom adecuado y una chincheta (marcador) con nombre.

Los Intent de mapas son "especialitos". Tienen este formato:
`geo:0,0?q=latitud,longitud(Nombre de la etiqueta)&z=zoom`

1. **¿Por qué `geo:0,0`?** Le decimos al mapa "no te centres en ninguna coordenada inicial, céntrate en lo que venga en la búsqueda (`q`)".
2. **El problema de los espacios:** La etiqueta "IES Severo Ochoa" tiene espacios. Las URLs **odian** los espacios. Si mandamos eso tal cual, el enlace se rompe.

**Solución:** Usar `URLEncoder`.

Ve al botón **"Ver en Google Maps"** y completa el `TODO`:

```kotlin
    // 1. Codificamos el nombre para que sea seguro (los espacios se convierten en %20, etc.)
    // IMPORTANTE: Necesitarás importar java.net.URLEncoder
    val encodedLabel = URLEncoder.encode(mapLabel, "UTF-8")

    // 2. Construimos la URI compleja concatenando las variables
    val geoUri = "geo:0,0?q=$latitude,$longitude($encodedLabel)&z=$mapZoom"

    // 3. Lanzamos
    uriHandler.openUri(geoUri)
```

Ahora, al pulsar, Maps entenderá perfectamente dónde ir y qué nombre mostrar.

### 1.3.6. Paso 5: WhatsApp (Intents manuales y Excepciones)

A veces `uriHandler` se queda corto o queremos más control. Para WhatsApp, vamos a implementar una función auxiliar `sendWhatsAppMessage` al final del archivo.

**Reto:** ¿Qué pasa si el usuario NO tiene WhatsApp instalado? Si intentamos abrirlo sin más, la app se cerrará de golpe (crash). Debemos controlar ese error.

Ve a la función `sendWhatsAppMessage` (al final del archivo) e impleméntala así:

```kotlin
fun sendWhatsAppMessage(context: Context, phoneNumber: String, message: String) {
    // 1. Limpieza: WhatsApp quiere el número sin '+' ni espacios (ej: 34666...)
    val cleanNumber = phoneNumber.replace("+", "").replace(" ", "")
    
    // 2. Codificamos el mensaje
    val encodedMessage = URLEncoder.encode(message, "UTF-8")
    
    // 3. Creamos la URI "mágica" de WhatsApp
    val uri = "https://wa.me/$cleanNumber?text=$encodedMessage"

    // 4. Creamos un Intent nativo ACTION_VIEW
    val intent = Intent(Intent.ACTION_VIEW)
    intent.data = android.net.Uri.parse(uri)

    /* TRUCO PRO: Si descomentas la siguiente línea, obligas a abrir WhatsApp oficial.
       Si la dejas comentada, Android preguntará al usuario (útil si usa WhatsApp Business) */
    // intent.setPackage("com.whatsapp")

    // 5. INTENTAMOS abrir la actividad
    try {
        context.startActivity(intent)
    } catch (e: ActivityNotFoundException) {
        // Si entramos aquí, es que no tiene WhatsApp instalado
        Toast.makeText(context, "WhatsApp no está instalado", Toast.LENGTH_SHORT).show()
    }
}
```

Ahora conecta esta función en el botón **"Mandar Whatsapp"** del Scaffold.

### 1.3.7. Paso 6: Ubicación y Permisos (lo más complejo)

Esta es la parte más compleja. La ubicación se considera un **permiso peligroso**. No basta con ponerlo en el Manifest; hay que pedirle permiso al usuario mediante una ventana emergente (diálogo) mientras usa la app.

**El "Launcher" de Permisos:**

En Compose, necesitamos registrar un "lanzador" que escuche la respuesta del usuario (¿Dijo SÍ o dijo NO?).
Ve al inicio de `IESSeveroOchoaIntents`, busca el **TODO Paso 5. Crear el permissionLauncher** y añade:

```kotlin
    // Preparamos el escuchador de permisos
    val permissionLauncher = rememberLauncherForActivityResult(
        contract = ActivityResultContracts.RequestMultiplePermissions()
    ) { permissions ->
        // Este código se ejecuta CUANDO el usuario responde al diálogo
        val isGranted = permissions[Manifest.permission.ACCESS_FINE_LOCATION] == true ||
                        permissions[Manifest.permission.ACCESS_COARSE_LOCATION] == true

        if (isGranted) {
            Toast.makeText(context, "Permiso concedido. Calculando...", Toast.LENGTH_SHORT).show()
            // ¡Llamamos a la función que calcula!
            calculateAndShowDistance(context, latitude, longitude)
        } else {
            Toast.makeText(context, "Se necesita permiso para calcular la distancia", Toast.LENGTH_LONG).show()
        }
    }
```

**Entendiendo `rememberLauncherForActivityResult` (El concepto clave)**

Hasta ahora, nuestro código era lineal: pulsábamos un botón y se abría una web. Fin.
Pero los **Permisos** son diferentes. Es una conversación de dos vías:

1. Tu App pregunta: "¿Puedo usar el GPS?"
2. Tu App **se queda esperando**.
3. El Usuario decide (puede tardar 1 segundo o 10 minutos).
4. Android vuelve a tu App con la respuesta: "Sí" o "No".

Para manejar esto en Compose, necesitamos "registrar" una oficina de recepción de respuestas antes de pedir nada. Eso es lo que hace `rememberLauncherForActivityResult`.

**Imagina que es como el "Busca" (Beeper) de los 100 Montaditos:**

- Tú llegas (se inicia la pantalla) y pides lo que quieres: Una de patatas 4 salsas, un 90...
- Pagas y el camarero te da un "Busca" (**creas el Launcher**).
- Tú te sientas a esperar.
- Cuando la mesa está lista, el aparato vibra y tú reaccionas a por tus patatas (**se ejecuta el código dentro de las llaves `{ }`**).

Vamos a hacer un forensics a este bloque de código para entenderlo de verdad:

```kotlin
val permissionLauncher = rememberLauncherForActivityResult(
    contract = ActivityResultContracts.RequestMultiplePermissions()
) { permissions -> 
    // ... código de respuesta ...
}
```

**1. `rememberLauncherForActivityResult`**:

- **¿Qué es?**: Es una función de Compose que "registra" nuestra petición al sistema operativo.
- **¿Por qué `remember`?**: En Compose, la pantalla se redibuja (recompone) constantemente. Si no usáramos `remember`, cada vez que la pantalla parpadeara, perderíamos la conexión con nuestra petición de permisos. Esto mantiene al "intermediario" vivo.

**2. `contract = ActivityResultContracts.RequestMultiplePermissions()`**:

- **El Contrato**: Aquí le decimos a Android **qué tipo de tarea** vamos a hacer. No es lo mismo pedir "Hacer una foto" (`TakePicture`) que "Pedir Permisos" (`RequestMultiplePermissions`).
- Al definir este contrato, Android ya sabe que cuando vuelva con la respuesta, debe traernos un mapa con los resultados de los permisos.

**3. `{ permissions -> ... }` (La Callback o "El Buzón")**:

- Todo lo que escribas entre estas llaves **NO se ejecuta ahora**.
- Es el código que se ejecutará **EN EL FUTURO**, justo en el momento en que el usuario pulse "Permitir" o "Denegar" en la ventana emergente.
- **La variable `permissions`**: Es el cartero. Es un `Map` (un diccionario) que contiene los pares de:
  - *Clave:* El nombre del permiso (ej. `ACCESS_FINE_LOCATION`).
  - *Valor:* `true` (concedido) o `false` (denegado).

**¿Cómo se usa después? (El botón):**

Una cosa es **contratar al mensajero** (lo que acabamos de hacer arriba) y otra es **mandarlo a trabajar**.

Ahora ve al botón **"Calcula distancia..."** y haz que lance la petición:

Por eso, el código anterior se pone al principio de la función, pero el "disparo" se hace en el botón:

```kotlin
// En el onClick del botón:
permissionLauncher.launch( // <--- ¡A trabajar!
    arrayOf(
        Manifest.permission.ACCESS_FINE_LOCATION,
        Manifest.permission.ACCESS_COARSE_LOCATION
    )
)
```

Al llamar a `.launch()`, es cuando realmente aparece la ventana emergente en la pantalla del usuario.

### 1.3.8. La Lógica Matemática (Google Play Services)

Por último, vamos a implementar la función `calculateAndShowDistance` al final del archivo. Aquí es donde ocurre la magia de `LocationServices`.

> **Atención:** Necesitarás importar muchas clases. Si sale en rojo, pulsa `Alt+Enter` e importa.
> `Priority` viene de `com.google.android.gms.location`. Ojo que muchas importaciones son ambiguas y toca decir, Locale por ejemplo viene de `java.util`.

```kotlin
private fun calculateAndShowDistance(context: Context, instituteLat: String, instituteLon: String) {
    // 1. Obtenemos el cliente de ubicación de Google
    val fusedLocationClient = LocationServices.getFusedLocationProviderClient(context)

    // 2. IMPORTANTE: Aunque el usuario haya dicho "Sí" antes, 
    // Android exige por seguridad volver a verificar el permiso antes de llamar a la API.
    if (ContextCompat.checkSelfPermission(context, Manifest.permission.ACCESS_FINE_LOCATION) == PackageManager.PERMISSION_GRANTED) {

        // 3. Pedimos la ubicación ACTUAL
        // PRIORITY_HIGH_ACCURACY: Usa GPS (gasta más batería, pero es exacto)
        fusedLocationClient.getCurrentLocation(Priority.PRIORITY_HIGH_ACCURACY, CancellationTokenSource().token)
            .addOnSuccessListener { userLocation: Location? ->
                if (userLocation != null) {
                    // A. Creamos la ubicación del Instituto
                    val instituteLocation = Location("provider").apply {
                        latitude = instituteLat.toDouble()
                        longitude = instituteLon.toDouble()
                    }

                    // B. Calculamos la distancia (magia matemática de Android)
                    val distanceInMeters = userLocation.distanceTo(instituteLocation)
                    val distanceInKm = distanceInMeters / 1000f

                    // C. Mostramos resultado
                    val msg = String.format(Locale.getDefault(), "Estás a %.2f km del instituto", distanceInKm)
                    Toast.makeText(context, msg, Toast.LENGTH_LONG).show()
                } else {
                    Toast.makeText(context, "No se pudo obtener la ubicación (GPS desactivado?)", Toast.LENGTH_SHORT).show()
                }
            }
            .addOnFailureListener {
                Toast.makeText(context, "Error al obtener ubicación", Toast.LENGTH_SHORT).show()
            }
    }
}
```

-----

**🔎 Forense de Código: `calculateAndShowDistance`**

Esta función es la encargada de hacer el trabajo sucio. Vamos a diseccionarla pieza a pieza porque aquí ocurren varias cosas "invisibles" que es vital entender. Muchas son específicas de la API de Google Play Services, pero bueno trabajar con temas de ubicación es relativamente común, por lo que las explicaremos. No te asustes, es normal no acordarse de esto hasta que te toque hacerlo en un proyecto real, que sepas que puedes volver aquí a repasarlo o buscar en la documentación oficial.

#### El Cliente Fusionado (`FusedLocationProviderClient`)

```kotlin
val fusedLocationClient = LocationServices.getFusedLocationProviderClient(context)
```

- **¿Qué es esto?** Antiguamente, en Android tenías que elegir: "¿Uso el GPS (preciso pero lento) o el Wi-Fi (rápido pero impreciso)?".
- **La solución de Google:** El `FusedLocationProvider` es un "cerebro" inteligente. Él decide automáticamente qué sensores combinar (fusionar) para darte la mejor ubicación posible ahorrando batería. Es la puerta de entrada a los servicios de ubicación.

#### El Doble Check de Seguridad (`checkSelfPermission`)

```kotlin
if (ContextCompat.checkSelfPermission(context, Manifest.permission.ACCESS_FINE_LOCATION) == PackageManager.PERMISSION_GRANTED) { ... }
```

- **La Pregunta:** *"¿Pero no habíamos pedido ya el permiso en el botón anterior?"*
- **La Respuesta:** Sí, pero **Android no se fía**. El usuario podría haber minimizado la app, ido a Ajustes y quitado el permiso hace 5 segundos.
- **La Regla:** Siempre, justo antes de ejecutar una línea de código que requiera permisos (`getCurrentLocation`), debes verificar si *siguen* concedidos. Si no pones este `if`, el compilador te marcará un error rojo (Lint Error) diciendo que es inseguro.

#### La Petición Asíncrona (`getCurrentLocation`)

```kotlin
fusedLocationClient.getCurrentLocation(Priority.PRIORITY_HIGH_ACCURACY, CancellationTokenSource().token)
```

Aquí pedimos la ubicación. Fíjate en dos detalles:

- **`PRIORITY_HIGH_ACCURACY`**: Le decimos: "Enciende el GPS, quiero precisión máxima".
- **`CancellationToken`**: Es un "token de cancelación". Es obligatorio pasarlo. Sirve por si quisieras cancelar la petición a medias (por ejemplo, si el usuario cierra la app antes de que el satélite responda), aunque aquí no lo usaremos activamente.

#### El Concepto de "Listener" (El que espera)

```kotlin
.addOnSuccessListener { userLocation: Location? -> ... }
```

Obtener la ubicación **tarda tiempo** (milisegundos o segundos). No podemos detener la app esperando al satélite (la pantalla se congelaría).

- Por eso usamos un **Listener**: un bloque de código que se ejecuta **cuando el dato está listo**.
- Le decimos a Android: *"Sigue con tu vida, y cuando tengas el dato, avísame ejecutando este bloque de código"*.
  - **El potencial `null`**: Fíjate que `userLocation` puede ser nulo (`?`). ¿Por qué?
    - El GPS está apagado.
    - Estás en un túnel.
    - El móvil acaba de reiniciarse y aún no sabe dónde está.
    - Por eso es **obligatorio** el `if (userLocation != null)`.

#### Matemáticas Geodésicas (`distanceTo`)

Tranquilo, casi todo viene ya enlatado en funciones que hacen las matemáticas duras por nosotros. Ten en cuenta que el tema de la geometría de la Tierra es complejo (esférica, elipsoide, etc.), a pesar de lo que algunos digan **NO es plana**, pero Android nos lo simplifica.

```kotlin
val instituteLocation = Location("manual").apply {
    latitude = instituteLat.toDouble()
    longitude = instituteLon.toDouble()
}
val distanceInMeters = userLocation.distanceTo(instituteLocation)
```

- **Crear un punto destino:** Para calcular la distancia, necesitamos dos puntos. El `userLocation` (que nos acaba de llegar) y el del instituto. Creamos un objeto `Location` manual metiéndole las coordenadas que teníamos guardadas arriba.
- **`distanceTo`:** Esta función es magia pura. Calcula la distancia en línea recta sobre la curvatura de la Tierra (usando fórmulas complejas como la de Haversine, que calcula la distancia *ortodrómica*, la más corta entre dos puntos en una esfera y que NO es una línea recta en un plano) y nos devuelve el resultado en **metros**.

#### El Toque Final (Formato)

```kotlin
String.format(Locale.getDefault(), "Estás a %.2f km", distanceInKm)
```

- Convertimos metros a kilómetros dividiendo por 1000.
- Usamos `String.format` para que solo muestre 2 decimales (`%.2f`). Además, al usar `Locale.getDefault()`, si el móvil está en España usará una coma (`15,40 km`) y si está en EEUU usará un punto (`15.40 km`). ¡Detalles de profesional\!

**Resumen Visual del Flujo:**

Para que que vosotros (y yo) podamos visualizarlo, el flujo de esta función es:

1. **START** -> ¿Tengo herramienta `fused`?
2. **CHECK** -> ¿Sigo teniendo permiso?
3. **REQUEST** -> "Satélite, dime dónde estoy (Alta Precisión)".
4. **WAIT** -> ... (La app sigue funcionando) ...
5. **CALLBACK** ->  Aquí tienes la ubicación (o null).
6. **CALCULATE** -> Distancia entre (Yo) y (Instituto).
7. **SHOW** -> Toast con el resultado (o el error).

### 1. El Endpoint

```http
GET https://pokeapi.co/api/v2/generation/{id}/
```

Donde `{id}` es el número de la generación (1 para Kanto, 2 para Johto, etc.).

**Ejemplo para la Generación 1:**
`https://pokeapi.co/api/v2/generation/1/`

### 2. ¿Qué te devuelve? (El JSON)

Aquí viene el "truco" para mantenerlo sencillo. Este endpoint devuelve un objeto grande, pero a ti solo te interesa la lista llamada `pokemon_species`.

El JSON se ve así (simplificado):

```json
{
  "id": 1,
  "name": "generation-i",
  "pokemon_species": [
    {
      "name": "bulbasaur",
      "url": "https://pokeapi.co/api/v2/pokemon-species/1/"
    },
    {
      "name": "charmander",
      "url": "https://pokeapi.co/api/v2/pokemon-species/4/"
    }
    // ... resto de la lista
  ]
}
```

-----

### 3. La Estrategia para las Imágenes (Importante)

Si te fijas, el JSON de arriba **no trae la imagen**, solo el `name` y una `url` de detalles.

Para **no complicarte** haciendo una segunda llamada a la API por cada Pokémon (lo cual sería lento y complejo para una práctica sencilla), usaremos un truco estándar con **Coil**:

1. Obtienes la lista de la generación.
2. Extraes el **ID** del Pokémon de la `url` (ej: de `.../pokemon-species/1/` sacas el `1`).
3. Construyes la URL de la imagen manualmente en tu Adapter usando el patrón oficial de los sprites de PokeApi:

> **URL de imagen directa:**
> `https://raw.githubusercontent.com/PokeAPI/sprites/master/sprites/pokemon/{id}.png`

De esta forma, Retrofit solo hace **una** llamada (la lista) y Coil se encarga de cargar las imágenes bajo demanda mientras haces scroll.

4. 🥘 **Paso 3: El Cocinado (Capa de Datos - Repositorio)**

Aquí se nos abre una disyuntiva. Podemos hacer que el ViewModel hable directamente (con el `Singleton` de *RetrofitClient*) con la API o podemos crear una capa intermedia llamada Repositorio que abstraiga la fuente de datos. La opción del repositorio es la más profesional y escalable, de hecho es la que se explica en el codelab oficial de Google, pero también es verdad que para prácticas sencillas se siente como un **overkill**. En esta práctica sientete libre de elegir la opción que más te guste, en lo profesional sí que te recomendaria usar el patrón de repositorio si la aplicación tiene visos de crecer en el futuro.

El tema de repositorio es especialmente útil si en el futuro queremos cambiar la fuente de datos (por ejemplo, usar una base de datos local o caché). Aquí vamos a crear un repositorio simple que hable con la API, por explicarlo alineado con el codelab. Podemos crear una clase llamada `PokemonRepository.kt` en el paquete `com.tuapp.data`.

El repositorio tiene dos partes:

- La interfaz (contrato) que define qué operaciones puede hacer el repositorio, y que implementarían todas las implementaciones concretas del mismo (por ejemplo, una que hable con la red, otra que hable con una base de datos local, etc).
- Las implementaciones concreta que habla con la API (o la base de datos, etc). Aquí inyectamos el servicio de Retrofit.

Esto es un patrón de diseño muy común en desarrollo de software llamado **Repository Pattern**.

```kotlin
// Interfaz para facilitar testing (Best Practice)
interface PokemonRepository{
    suspend fun getGenerationPokemons(generation: Int): List<PokemonDto>
    suspend fun getGenerations(): List<GenerationDto>
}

// Implementación concreta. Inyectamos el servicio, no lo creamos aquí
class NetworkPokemonRepository(
    private val apiService: PokeApiService
): PokemonRepository {
    override suspend fun getGenerationPokemons(generation: Int): List<PokemonDto> {
        return apiService.getGenerationPokemons(generation).pokemons
    }


    override suspend fun getGenerations(): List<GenerationDto> {
        return apiService.getGenerations().results
    }
}
```

5. 📦 **Paso 4: El Contenedor (Manual Dependency Injection)**

Como hemos comentado alternativamente podrías implementar el ViewModel para que hable directamente con el servicio de Retrofit (vía un singleton `RetrofitClient`), pero si has optado por el patrón de repositorio, necesitamos una forma de inyectar el repositorio en el ViewModel. Para ello, vamos a crear un contenedor de dependencias manual muy simple. En proyectos reales se usan librerías como **Hilt** o **Koin**, pero para prácticas sencillas esto es suficiente. Estas cosas las comento para que os suenen, por si en el futuro tenéis que buscar que sepáis por dónde.

Para la inyección manual de dependencias, creamos un objeto llamado `AppContainer.kt` en el paquete `com.tuapp.di` (dependency injection) o `com.tuapp.data`.

De nuevo esto trae dos partes:

- La interfaz que define qué dependencias expone el contenedor (en este caso solo el repositorio).
- La implementación concreta que crea las dependencias (el servicio de Retrofit y el repositorio). Aquí aprovechamos para indicar también la configuración de Retrofit (base URL, convertidor, etc). Fijate que usamos `by lazy` para inicializar las dependencias solo cuando se usan por primera vez (Best Practice). **Especial atención** a la línea de ignoreUnknownKeys en el Json, que evita fallos si la API devuelve campos extra que no tenemos en nuestros DTOs.

```kotlin
interface AppContainer {
    val pokemonRepository: PokemonRepository
}

class DefaultAppContainer: AppContainer {
    private val baseUrl = "https://pokeapi.co/api/v2/"

    //Empezamos a inicializar primero Retrofit, siempre lazy.
    private val retrofit: Retrofit by lazy {
        Retrofit.Builder()
            .addConverterFactory(Json {
                ignoreUnknownKeys = true
            }.asConverterFactory("application/json".toMediaType()))
            .baseUrl(baseUrl)
            .build()
    }

    private val retrofitService: PokeApiService by lazy {
        retrofit.create(PokeApiService::class.java)
    }

    override val pokemonRepository: PokemonRepository by lazy {
        NetworkPokemonRepository(retrofitService)

    }
}
```

Este paso es el más pesado, por eso todavía quedan cosas, ahora tenemos que instanciar esto en una clase que extienda de `Application`, para que esté disponible en toda la app. Creamos una clase llamada `PokemonApplication.kt` en el paquete raíz `com.tuapp`.

```kotlin
class PokemonApplication: Application() {

    lateinit var container: AppContainer
    override fun onCreate() {
        super.onCreate()
        container = DefaultAppContainer()
    }
}
```

Probablemente sea incluso buena idea juntarla con MainActivity o con PokemonApp.kt, pero por replicar el codelab he preferido dejarlo separado.

Por último, que no se te olvide registrar esta clase en el Manifest:

```xml

    ... >
```

Esas tres cosas son las que hacen que la inyección manual de dependencias funcione.

6. **👨‍🍳 Paso 5: El Chef (Capa de Presentación - ViewModel)**

El vista modelo ya lo conocéis de sobra a estas alturas pero, aprovechando que el codelab lo introducía, vamos a usar el tema de las **Sealed Interfaces**. Esto es una Best Practice muy recomendable para evitar estados inconsistentes en la UI.

En el típico archivo `PokemonUiState.kt` en el paquete `com.tuapp.ui` definimos el estado de la UI. Aquí es donde usamos una **clase de datos** para los datos persistentes (como la generación seleccionada) y una **sealed interface** para los estados exclusivos de la petición (Cargando, Error, Datos).

```kotlin
 UiState: Una sola clase que lo tiene todo
data class PokemonUiState(
    // Datos de la pantalla (persisten siempre)
    val selectedGeneration: Int = 1,
    val generations: Int = 1, // Podríamos poner 9 pero la gracia es que lo recupere de la API.
    // Estado de la petición (aquí usamos la lógica excluyente para la lista)
    val requestStatus: RequestStatus = RequestStatus.Idle  // Esto es lo mismo que hace el codelab con MarsPhoto
)

// Estado exclusivo solo para la carga de datos
sealed interface RequestStatus {
    ...
    data class Success(val pokemons: List<PokemonDto>) : RequestStatus
    object Error : RequestStatus
}
```

Fíjate como el tema de las listas de pokémons lo hemos metido dentro del estado exclusivo `RequestStatus`. De esta forma, si el estado es `Loading` o `Error`, no hay lista de pokémons, y si es `Success`, la lista siempre está presente. Esto evita estados inconsistentes en la UI (por ejemplo, tener una lista visible pero el estado en `Loading`).

Ten en cuenta que no te doy las clases enteras pueden que falten cosas pero para que la idea se entienda.

### Alternativa: Acceso estático con Singleton (RetrofitClient)

Pues si optamos por esa vía, sacrificamos el tema de la inyección de dependencias y el contenedor, y hacemos que el ViewModel hable directamente con el servicio de Retrofit a través de un Repository fake. Este repositorio lo que hace es usar un singleton `RetrofitClient` que crea el servicio de Retrofit internamente. El repository no lo inyectamos, lo creamos directamente en el ViewModel.

Una posible implementación del singleton `RetrofitClient` y el repositorio `PokemonRepository` sería:

```kotlin

// EL SINGLETON RETROFITCLIENT
object RetrofitClient {

   
    private const val BASE_URL = "https://pokeapi.co/api/v2/"

    private val json = Json {
        ignoreUnknownKeys = true
    }

    //Empezamos a inicializar primero Retrofit, siempre lazy.
    private val retrofit: Retrofit by lazy {
        Retrofit.Builder()
            .addConverterFactory(json.asConverterFactory("application/json".toMediaType()))
            .baseUrl(baseUrl)
            .build()
            .create(PokemonApiService::class.java)
    }
}


object PokemonRepository {
    
    // El Repositorio usa al cliente internamente.
    // Si mañana cambiamos Retrofit por otra cosa, el ViewModel ni se entera.
    private val api = RetrofitClient.service

    suspend fun getGenerations(): List<GenerationDto> {
        // Aquí podríamos filtrar, ordenar o guardar en caché
        return api.getGenerations().results
    }

    suspend fun getPokemon(id: Int): PokemonDto {
        return api.getPokemon(id)
    }
}
```

La ganancia principal de hacerlo por el camino del Repositorio auténtico es que el ViewModel no depende directamente de Retrofit, sino de una abstracción (el repositorio). Esto facilita el testing y la escalabilidad futura. Evidentemente, no va a ser nuestro caso en este curso pero por daros al menos un ejemplo de buenas prácticas. Aún con todo y con eso, la *inyección manual de dependencias* tampoco es el *endgame*, el siguiente paso lógico sería usar una librería de inyección de dependencias como Hilt o Koin para no tener que hacer la inyección manualmente.

Si te interesa el tema de la inyección de dependencias, el codelab de la Inventory App que se trabaja en el tema de Room [https://developer.android.com/codelabs/basic-android-kotlin-compose-persisting-data-room](https://developer.android.com/codelabs/basic-android-kotlin-compose-persisting-data-room) tiene una implementación de inyección de dependencias manual, con viewmodel dedicado para cada pantalla, navegación con saveStateHandle, etc. Sin ser especialmente compleja es una app bastante completa y profesional. Además el tema de base de datos estratégicamente lo llama **OfflineItemsRepository** para que veáis que en el mundo real las apps no solo hablan con la red, sino que también tienen una base de datos local para funcionar offline.
